# Ubuntu Hardening Script — VPS/VDS Edition (v4.0)

Скрипт автоматизированного харденинга Ubuntu 22.04 / 24.04 / 26.04 для виртуальных серверов.
Запускается от `root` сразу после получения чистого VPS/VDS и проводит полную настройку безопасности в один проход. Работает интерактивно или без вопросов (`--config … --yes`), умеет выполнять отдельные шаги, проверять состояние (`--audit`) и откатывать свои изменения (`--rollback`). Отдельный режим `--luks` добавляет шифрование LUKS2 — от отдельных дисков до всего сервера.

Основан на практиках **CIS Ubuntu Linux Benchmark** с поправками на специфику VPS: физического доступа нет, консоль — только через панель провайдера, поэтому все меры, способные «уронить» сервер в офлайн (паника ядра при сбое аудита, пароль GRUB, агрессивный blacklist драйверов), либо смягчены, либо сознательно исключены. Каждое такое решение задокументировано в разделе [Сознательные отклонения от CIS](#сознательные-отклонения-от-cis).

## Что нового в v4

Полная история (v2, v3, v3.1) — в [CHANGELOG.md](CHANGELOG.md).

**Новые режимы**

| Возможность | Суть |
|---|---|
| **Неинтерактивный запуск** | `--config <файл> --yes`: все ответы берутся из файла (`КЛЮЧ=значение`), окружения (`UH_КЛЮЧ`) или прошлого прогона. Подходит для cloud-init, Ansible, CI. См. [раздел](#неинтерактивный-режим) |
| **Выбор шагов** | `--only ssh,ufw` / `--skip mounts`, список — `--list-steps`. При сбое скрипт печатает команду для продолжения с упавшего шага |
| **Проверка `--audit`** | Только чтение: сверяет итоговые `sshd -T`, sysctl (файл против ядра), флаги монтирования, UFW, auditd, AppArmor, обновления. Код возврата 1 при FAIL — годится для cron и мониторинга |
| **Откат `--rollback`** | Каждый прогон сохраняет исходные файлы в `/var/backups/ubuntu_hardening/<метка>/` с манифестом; откат восстанавливает их, удаляет созданные файлы и возвращает отключённые юниты |
| **Итог по факту** | Таблица в конце показывает реальный статус каждого шага: выполнен, с предупреждениями, выключен настройкой или пропущен (в v3 всегда печаталось `[OK]`) |

**Исправленные ошибки v3**

| Ошибка | Суть и исправление |
|---|---|
| **`/var/log/sudo.log` не пополнялся** | Файл создавался `root:root 600`, а rsyslog в Ubuntu пишет от имени `syslog`. Теперь `syslog:adm 640`, добавлена ротация, события sudo остаются и в `auth.log` |
| **Дубли в `limits.conf`** | Проверка искала `hard core` с одним пробелом, а записывались строки с четырьмя — при каждом запуске добавлялись три строки. Теперь отдельный файл `limits.d/99-ubuntu-hardening-core.conf`, старые строки убираются |
| **Расчётный audit backlog не применялся** | `augenrules` оставляет последний `-b`, а `audit.rules` дистрибутива читается после `99-*.rules` — побеждал его `-b 8192`. Теперь `-b`, `-f`, `-e` вынесены в `zz-hardening-finalize.rules` (проверено на `augenrules` 24.04) |
| **auditd пропускался целиком при immutable** | При `enabled 2` v3 не записывала даже файлы, и смена администратора или версии скрипта не доходила до правил. Теперь файлы пишутся всегда, пропускается только загрузка |
| **`grep -q` в пайпах под `pipefail`** | `producer \| grep -q` мог вернуть «не найдено» из-за SIGPIPE у источника (проверка часового пояса, порта, имени службы). Заменено на here-string и фильтры `ss` |
| **ERR-trap не работал в функциях** | Без `set -E` сбой внутри любой `luks_*`-функции завершал скрипт без номера строки. Добавлены `set -E`, `EXIT`-обработчик (временные файлы, дочитывание лога) и вывод упавшей команды |
| **initramfs на 26.04** | Секция 11 вызывала `update-initramfs`, которого на dracut нет, и прятала ошибку. Теперь — общий `luks_regen_initramfs` с выводом ошибки |
| **apt падал на свежем VPS** | cloud-init и unattended-upgrades держат блокировку dpkg первые минуты. Теперь скрипт ждёт `cloud-init status --wait`, а apt — `DPkg::Lock::Timeout=300` |

**Безопасность и совместимость**

| Изменение | Суть |
|---|---|
| **Ключи root → администратору** | Новый вариант по умолчанию: ключи из `/root/.ssh/authorized_keys` (опции вроде `command="…"` из cloud-образов отбрасываются). Генерация ключа на сервере больше не вариант по умолчанию |
| **SSH** | `AllowAgentForwarding no`, `PermitTunnel no`, `PermitUserEnvironment no`, `HostbasedAuthentication no`, `IgnoreRhosts yes`, `internal-sftp`; порт 22 допустим |
| **Docker и UFW** | Docker публикует порты в обход UFW — добавляется цепочка `DOCKER-USER`, открытыми остаются только перечисленные порты контейнеров (по умолчанию — уже опубликованные, чтобы не уронить сервисы). Форвардинг ядра включается автоматически при Docker/Podman/LXD/WireGuard |
| **Малая RAM** | При RAM < 2 ГБ `/tmp` остаётся на диске (bind с `noexec`) вместо tmpfs |
| **Настраиваемые меры** | `HOME_NOEXEC`, `IPV6_ACCEPT_RA` (по умолчанию RA сохраняется при глобальном IPv6), `LOG_MARTIANS`, `DNSSEC_MODE` (по умолчанию `no`: `allow-downgrade` в systemd-resolved бывает нестабилен) |
| **chrony, pwquality** | Drop-in файлы вместо перезаписи файлов дистрибутива; `chrony.conf`, перезаписанный v3, восстанавливается из пакета. Штатные NTP-источники Ubuntu (на новых выпусках — с NTS) сохраняются |
| **auditd** | b32 для `access` и `kexec`, `openat2`/`open_by_handle_at`, `fchmodat2`, `renameat2` (отдельными правилами), удаление/переименование, xattr, запуск каждой SUID/SGID-программы (CIS), `sudo.log` |
| **Учётные записи** | `login.defs`: `UMASK 027`, срок пароля, `YESCRYPT` (24.04+); необязательный `pam_faillock` (проверен `pamtester`: блок после 5 ошибок, сброс `faillock --reset`) |
| **Прочее** | journald с квотой и `Storage=persistent`; пересылка syslog и auditd (`REMOTE_SYSLOG`); снятие SUID через `dpkg-statoverride` (переживает обновления); расширенный blacklist модулей; необязательные AIDE, `hidepid`, параметры ядра в GRUB; отчёт о лишних службах и слушающих портах; IPv6 DNS; проверка `ID=ubuntu` |

**Исправление к обзору v3.** В обзоре предполагалось, что `Package-Blacklist` с `"mysql"` задерживает и `libmysqlclient*`. Это не так: unattended-upgrades сравнивает через `re.match`, то есть от начала имени. Список оставлен без изменений.

## Требования

| Параметр | Значение |
|---|---|
| ОС | Ubuntu 22.04 / 24.04 / 26.04 LTS |
| Платформа | VPS / VDS (KVM, XEN, VMware, Hyper-V) |
| Пользователь | `root` |
| Сеть | Доступ в интернет для установки пакетов |
| Доступ | VNC или консоль провайдера на случай потери SSH |

ОС проверяется при старте по `/etc/os-release`: требуется `ID=ubuntu`; для 22.04 / 24.04 / 26.04 скрипт продолжает без вопросов, для другой версии — запрашивает подтверждение (в `--yes` — нужен `ALLOW_UNTESTED_OS=yes`).

> ⚠️ **Перед запуском убедитесь, что у вас открыта консоль провайдера (VNC/KVM).** Если SSH-сессия оборвётся в процессе, вы сможете продолжить через неё. Особенно это важно на этапах смены порта SSH и блокировки root.

## Быстрый старт

```bash
# Скачать скрипт на сервер
wget -O ubuntu_hardening.sh https://raw.githubusercontent.com/borross/ubuntu_hardening/refs/heads/main/ubuntu_hardening.sh

# Проверить содержимое перед запуском
less ubuntu_hardening.sh

# Запустить
bash ubuntu_hardening.sh

# Или без вопросов — все ответы в файле (см. example.conf)
bash ubuntu_hardening.sh --config /root/hardening.conf --yes

# После перезагрузки — проверить результат
bash ubuntu_hardening.sh --audit
```

Ссылка ведёт на ветку `main`. Для продакшна закрепите конкретный коммит (`…/ubuntu_hardening/<commit>/ubuntu_hardening.sh`) и сверьте `sha256sum`, чтобы повторные развёртывания запускали проверенную версию.

В интерактивном режиме вопросы (администратор, порт SSH, ключ, имя хоста, FQDN, DNS, часовой пояс, NTP, порты UFW) задаются в начале, до изменений; `Enter` принимает значение по умолчанию. Без терминала (`curl … | bash`, cloud-init) скрипт работает только с `--yes`.

Весь вывод дублируется в лог `/root/hardening_harden_<дата>_<время>.log` (права `600`) — при разборе проблем это первое, куда стоит смотреть. Приватный ключ и пароли в лог не попадают. При аварийной остановке печатаются номер строки и команда, шаг, на котором остановился скрипт, команда для продолжения (`--only …`) и команда отката.

## Аргументы командной строки

```bash
bash ubuntu_hardening.sh                          # полный харденинг (интерактивно)
bash ubuntu_hardening.sh --config my.conf --yes   # без вопросов
bash ubuntu_hardening.sh --only sysctl,auditd     # выбранные шаги
bash ubuntu_hardening.sh --audit                  # проверка без изменений
bash ubuntu_hardening.sh --rollback [метка]       # откат файлов прогона
bash ubuntu_hardening.sh --luks <режим> ...       # только шифрование LUKS2
bash ubuntu_hardening.sh --help | --version | --list-steps
```

| Опция | Назначение |
|---|---|
| `--config <файл>` | значения настроек, формат `КЛЮЧ=значение` ([список](#переменные-конфигурации), пример — `example.conf`). Файл читается построчно, **не через `source`**: код из него не выполняется, неизвестные ключи пропускаются с предупреждением |
| `-y`, `--yes` | не задавать вопросов. Требует ключ (ключи root или `SSH_PUBKEY`) и, для нового пользователя, `ADMIN_PASSWORD_HASH`. Шифрование LUKS в этом режиме не выполняется |
| `--only <шаги>` / `--skip <шаги>` | выполнить только эти шаги / все, кроме этих (имена через запятую) |
| `--list-steps` | список шагов с номерами секций |
| `--audit` | проверка текущего состояния; код 1, если есть FAIL |
| `--rollback [метка]` | без метки — список прогонов; с меткой — откат |

Шаги: `packages host key user ssh root ufw fail2ban cron mounts sysctl modules coredump auditd apparmor sudo accounts perms telemetry updates journald aide luks finish` — по одному на секцию ниже.

| Режим `--luks` | Что делает |
|---|---|
| `status` | Состояние шифрования: root, тома, swap, crypttab, AES-NI |
| `data <устройство>` | Зашифровать отдельный диск/раздел (**данные удаляются**) |
| `file <путь> <размер>` | Файл-контейнер, например `/var/lib/secure.img 20G` |
| `swap` | Убрать открытый swap: файл → zram, раздел → dm-crypt со случайным ключом |
| `remote-unlock` | Ввод пароля root-LUKS по сети: dropbear в initramfs (22.04/24.04) или Tang (26.04) |
| `docker` | Перенести данные Docker/containerd на зашифрованный том (создайте его заранее: `data` или `file`) |
| `encrypt-root <раздел>` | Зашифровать корень из rescue-системы; если `/boot` внутри корня — создать раздел `/boot` |
| `encrypt-root-auto` | Зашифровать корень с работающей системы при следующей загрузке (нужен отдельный `/boot`, 22.04/24.04) |
| `encrypt-root-finish` | После такой загрузки: задать пароль, удалить временный ключ |
| `encrypt-root-cancel` | Отменить подготовку `encrypt-root-auto` |

| Опция `--luks` | По умолчанию | Назначение |
|---|---|---|
| `--name <имя>` | `securedata` | имя маппинга `/dev/mapper/<имя>` |
| `--mount <путь>` | `/srv/secure` | точка монтирования |
| `--fs ext4\|xfs` | `ext4` | файловая система |
| `--mount-opts <опции>` | `defaults,nodev,nosuid` | опции монтирования |
| `--unlock manual\|keyfile\|tang` | `manual` | способ разблокировки при загрузке |
| `--tang <URL>` | — | Tang-сервер (для `--unlock tang` и root) |
| `--discards` | выкл. | TRIM (раскрывает занятые блоки) |
| `--no-perf` | — | не использовать `no_read/no_write_workqueue` |
| `--prefill` | выкл. | заполнить том через dm-crypt |
| `--cipher`, `--key-size` | `aes-xts-plain64`, `512` | шифр |
| `--user <имя>` | из `/etc/ubuntu_hardening.conf` | чьи ключи пускать в initramfs |
| `--dropbear-port <n>` | `2222` | порт SSH в initramfs |
| `--prepare` | — | `remote-unlock` до шифрования root |

Подробности — в разделе [Шифрование LUKS](#шифрование-luks-режим---luks) и в `LUKS.md`.

## Переменные конфигурации

Значения задаются (по возрастанию приоритета): в начале скрипта → в `/etc/ubuntu_hardening.conf` от прошлого прогона → в файле `--config` → в окружении с префиксом `UH_` (например `UH_SSH_PORT=2222`). В интерактивном режиме они же показываются как ответ по умолчанию: `Enter` — принять, `-` — очистить.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `ADMIN_USER` | `admin` | имя администратора (лучше неочевидное) |
| `SSH_PORT` | `20202` | `22` или 1024–65535 |
| `SSH_KEY_SOURCE` | `root`, если есть ключи root | `root` \| `provided` \| `ed25519` \| `ecdsa-521` |
| `SSH_PUBKEY` | — | строка публичного ключа для `provided` |
| `ADMIN_PASSWORD_HASH` | — | crypt-хеш пароля для `--yes` (`openssl passwd -6`) |
| `NEW_HOSTNAME`, `NEW_FQDN`, `TIMEZONE` | — | пусто — не менять |
| `DNS_SERVERS` | — | IPv4/IPv6 через пробел; пусто — не менять |
| `DNSSEC_MODE` | `no` | `no` \| `allow-downgrade` \| `yes` |
| `NTP_SERVERS` | — | свои NTP-серверы (добавляются к штатным) |
| `NTP_REPLACE_DEFAULTS` | `no` | `yes` — только `NTP_SERVERS` |
| `NTP_ADD_NTS` | `yes` | добавить `time.cloudflare.com` с NTS |
| `EXTRA_PORTS` | — | дополнительные порты UFW: `80 443 51820/udp 8000:8100/tcp` |
| `DOCKER_UFW_FIX` | `auto` | цепочка `DOCKER-USER`: `auto` (при Docker) \| `yes` \| `no` |
| `DOCKER_ALLOW_PORTS` | `auto` | порты **контейнеров**, открытые извне; `auto` — уже опубликованные |
| `FAIL2BAN_IGNOREIP` | — | свои IP/подсети, которые не банятся |
| `SSH_ADDRESS_FAMILY` | `any` | `inet` — только IPv4 (**не ставьте на IPv6-only VPS**) |
| `TCP_FORWARDING`, `AGENT_FORWARDING`, `GATEWAY_PORTS`, `X11_FORWARDING` | `no` | форвардинг SSH |
| `IP_FORWARD` | `auto` | форвардинг ядра: `auto` (при Docker/Podman/LXD/WireGuard) \| `yes` \| `no` |
| `TMP_MODE` | `auto` | `/tmp`: `auto` (tmpfs при RAM ≥ 2 ГБ) \| `tmpfs` \| `disk` |
| `HOME_NOEXEC` | `yes` | `noexec` на `/home` |
| `IPV6_ACCEPT_RA` | `auto` | `auto` — сохранить RA при глобальном IPv6 \| `yes` \| `no` |
| `LOG_MARTIANS` | `yes` | логировать martian-пакеты |
| `APPARMOR_ENFORCE_ALL` | `no` | перевести complain-профили в enforce |
| `PASSWORD_CLASSES` | `yes` | требовать все классы символов (CIS); `no` — только длина (NIST) |
| `PASSWORD_MAX_DAYS` | `365` | срок пароля администратора |
| `ENABLE_FAILLOCK` | `no` | блокировка после 5 неверных паролей sudo/su |
| `ENABLE_AIDE` | `no` | контроль целостности AIDE |
| `KERNEL_CMDLINE_HARDENING` | `no` | `slab_nomerge init_on_alloc=1 page_alloc.shuffle=1 vsyscall=none` |
| `HIDEPID` | `no` | `/proc` с `hidepid=invisible` |
| `REMOTE_SYSLOG` | — | `host:port` — пересылка syslog и auditd по TCP (без TLS) |
| `DISABLE_SERVICES` | — | для `--yes`: какие лишние службы отключить |
| `ALLOW_UNTESTED_OS` | `no` | разрешить запуск на непроверенной версии/ОС |

Не через конфиг (только в начале скрипта): `KEY_PATH`, `STATE_FILE`, `BACKUP_ROOT` и значения по умолчанию LUKS — их удобнее задавать опциями `--luks`.

## Интерактивные вопросы и контрольные точки

Все вопросы, кроме паролей и контрольной точки, задаются **в начале**, до первых изменений: дальше скрипт работает без внимания, а неверный ответ не оставит систему настроенной наполовину. Задаются только вопросы выбранных шагов.

| Когда | Вопрос | По умолчанию |
|---|---|---|
| Начало | Имя администратора | `admin` / прошлый прогон |
| Начало | Порт SSH (`22` или 1024–65535) | `20202` / прошлый прогон |
| Начало | Ключ: **ключи root** / свой публичный / сгенерировать ed25519 / ecdsa-521 | ключи root, если они есть, иначе ed25519 |
| Начало | Имя хоста, FQDN, часовой пояс, DNS (IPv4/IPv6), свои NTP и «только они?» | не менять |
| Начало | Дополнительные порты UFW; при Docker — порты контейнеров, открытые извне | только SSH / уже опубликованные |
| Секция 2 | Пароль приватного ключа (только при генерации), пауза «сохраните ключ» | — |
| Секция 3 | Пароль администратора (для sudo); при повторном запуске — «сменить?» | обязателен для нового пользователя |
| Секция 4 | **Контрольная точка**: «вход под администратором работает?» `y/n` | `n` прерывает скрипт **до** блокировки root |
| Секция 19.5 | Шифрование LUKS | пропустить |
| Секция 20 | Показать/удалить сгенерированный ключ; отключить найденные лишние службы | `N` |

Контрольная точка — главный предохранитель: root блокируется только после того, как вы из **нового терминала** подтвердили вход под администратором на новом порту. Если шаг `ssh` в прогон не входит, а `root` входит — контрольная точка выполняется перед блокировкой root.

## Неинтерактивный режим

```bash
# хеш пароля для sudo (сам пароль в файл не пишется)
openssl passwd -6
cp example.conf /root/hardening.conf && chmod 600 /root/hardening.conf
nano /root/hardening.conf
bash ubuntu_hardening.sh --config /root/hardening.conf --yes
```

Минимальный файл:

```ini
ADMIN_USER=opsadm
SSH_PORT=22022
SSH_PUBKEY="ssh-ed25519 AAAA... me@laptop"   # или SSH_KEY_SOURCE=root
ADMIN_PASSWORD_HASH='$6$...'
EXTRA_PORTS="80 443"
```

В cloud-init (`runcmd`) или CI вместо файла можно передать переменные `UH_*`. Особенности `--yes`:

- ключ нельзя сгенерировать — его некому сохранить; нужен `SSH_PUBKEY` или ключи root;
- контрольную точку проходит автоматическая проверка: `sshd -T` для администратора (`publickey`, `AllowUsers`), порт слушается, в `authorized_keys` есть действующий ключ. Человеком вход не подтверждён — это видно в итоге как предупреждение шага `ssh`;
- LUKS пропускается (деструктивные операции требуют подтверждения);
- лишние службы отключаются только перечисленные в `DISABLE_SERVICES`.

## Выбор шагов

```bash
bash ubuntu_hardening.sh --list-steps
bash ubuntu_hardening.sh --only sysctl,modules        # только ядро
bash ubuntu_hardening.sh --skip mounts,telemetry      # всё, кроме этого
```

Шаги без `ssh` берут порт и администратора из `/etc/ubuntu_hardening.conf`, так что `--only ufw,fail2ban` откроет правильный порт. Если шаг падает, скрипт печатает, на каком шаге остановился, и готовую команду `--only <этот и оставшиеся>` для продолжения после исправления.

## Проверка (--audit)

```bash
sudo bash ubuntu_hardening.sh --audit
```

Ничего не меняет и не пишет лог. Проверяет: итоговую конфигурацию sshd для администратора (`sshd -T -C`), `ssh.socket`, ключи, блокировку root, `pam_wheel`, pwquality, sudoers и права `sudo.log`, UFW (включён, `deny incoming`, правило SSH, Docker), fail2ban, **каждый параметр `99-hardening.conf` против текущего значения ядра**, загруженные модули из blacklist, флаги `/tmp`, `/dev/shm`, `/var/tmp`, `/home`, auditd (immutable, число правил, потерянные события), AppArmor, journald, автообновления, ожидающие пакеты и нужна ли перезагрузка. Код возврата 1, если есть хоть один FAIL — удобно для cron или системы мониторинга:

```bash
# /etc/cron.d/hardening-audit
0 6 * * * root bash /root/ubuntu_hardening.sh --audit >/var/log/hardening-audit.log 2>&1 || logger -t hardening "audit FAIL"
```

## Откат (--rollback)

Перед изменением любого файла скрипт копирует его в `/var/backups/ubuntu_hardening/<метка>/files/` (с полным путём) и записывает в `manifest`: `saved <путь>` — файл был, `new <путь>` — файл создан, а также отключённые юниты и снятые SUID.

```bash
bash ubuntu_hardening.sh --rollback                     # список прогонов
bash ubuntu_hardening.sh --rollback 20261123_114329     # откат
```

Откат идёт в обратном порядке: файлы восстанавливаются, созданные удаляются, юниты включаются обратно, `dpkg-statoverride` снимается. Затем — `sysctl --system`, проверка `sshd -t` и перезапуск sshd, `ufw reload` (или `disable`, если UFW был выключен), перезапуск rsyslog/chrony/fail2ban.

**Не откатываются:** пользователи и пароли (в том числе блокировка root — `passwd root` задаёт новый пароль), удалённые пакеты телеметрии, неизменяемые правила auditd (до перезагрузки), LUKS. Изменения fstab и модулей вступают в силу после перезагрузки.

## Что делает скрипт

Нумерация секций соответствует выводу скрипта.

### 0. Предстартовые проверки и обновление системы

**Проверки:** запуск от root; терминал (без него — только с `--yes`); `ID=ubuntu` и версия по `/etc/os-release` (иное — с подтверждением или `ALLOW_UNTESTED_OS=yes`); валидация всех настроек из `--config`/`UH_*`.

**cloud-init и apt.** На только что созданном VPS cloud-init ещё работает и вместе с unattended-upgrades держит блокировку dpkg. Скрипт ждёт `cloud-init status --wait` (до 10 минут), а каждый вызов apt — `-o DPkg::Lock::Timeout=300`, вместо того чтобы упасть на первом `apt-get update`.

**Расчёт лимитов логирования** — до начала изменений:

```
Квота логов  = свободное место на разделе /var/log ÷ 10   (10%, зажато 50–2048 МБ)
               делится на 5 файлов ротации auditd; та же квота — для journald
Audit backlog = RAM_МБ × 8                                 (зажато 8192–65536)
```

| RAM VPS | Backlog |
|---|---|
| 512 МБ – 1 ГБ | 8192 (минимум) |
| 2 ГБ | 16384 |
| 4 ГБ | 32768 |
| 8 ГБ+ | 65536 (максимум) |

Backlog — буфер в **оперативной памяти** ядра, поэтому считается от RAM, а не от диска.

**Шаг `packages`:** `apt-get upgrade` в неинтерактивном режиме (`--force-confdef`/`--force-confold`) и установка:

```
ufw  fail2ban  auditd  audispd-plugins  libpam-pwquality  unattended-upgrades  apt-listchanges
acl  curl  wget  gnupg2  chrony  rsyslog  needrestart  apparmor  apparmor-utils
```

Каждый следующий шаг сам доустанавливает нужные ему пакеты, поэтому `--only`/`--skip packages` работают. Если обновление требует перезагрузки, шаг завершается с предупреждением.

### 1. Имя хоста, FQDN, DNS, часовой пояс, NTP

**Имя хоста** — `hostnamectl set-hostname`, валидация по RFC 1123. Строка `127.0.1.1` в `/etc/hosts` заменяется — без неё `sudo` выдаёт `unable to resolve host`.

**FQDN** — запись в `/etc/hosts`:

```
127.0.1.1    server01.example.com  server01
```

**cloud-init.** Если он установлен, пишется `/etc/cloud/cloud.cfg.d/99-ubuntu-hardening.cfg` с `preserve_hostname: true` и `manage_etc_hosts: false` — иначе при перезагрузке cloud-init вернул бы имя хоста и `/etc/hosts` из метаданных провайдера.

**DNS** — один или несколько адресов IPv4/IPv6 через пробел (IPv6 проверяется модулем Python `ipaddress`):

| Провайдер | Адреса |
|---|---|
| Cloudflare | `1.1.1.1 1.0.0.1 2606:4700:4700::1111` |
| Quad9 | `9.9.9.9 149.112.112.112` |
| Google | `8.8.8.8 8.8.4.4` |

При активном `systemd-resolved` — drop-in `/etc/systemd/resolved.conf.d/custom-dns.conf` с DNS-over-TLS `opportunistic` и `DNSSEC=${DNSSEC_MODE}` (по умолчанию `no`: режим `allow-downgrade` в systemd-resolved известен периодическими сбоями разрешения). DNS провайдера, полученные по DHCP, остаются у интерфейса и тоже используются; чтобы исключить их, в netplan задайте `dhcp4-overrides: { use-dns: false }` (и `dhcp6-overrides`) и выполните `netplan apply`.

Без systemd-resolved — запись в `/etc/resolv.conf` с предупреждением, что DHCP-клиент может её перезаписать. `chattr +i` из v3 **снимается**: неизменяемый файл ломает DHCP и обновления пакетов.

**Часовой пояс** — `timedatectl set-timezone`, значение проверяется по `timedatectl list-timezones`.

**NTP через chrony.** Chrony предпочтительнее `systemd-timesyncd` на VPS: быстрее догоняет после долгого простоя, `maxdistance` отсекает плохие источники. **Файл пакета `chrony.conf` не перезаписывается** (v3 заменяла его целиком и теряла штатные источники; такой файл восстанавливается из `/usr/share/chrony/chrony.conf`). Вместо этого:

- `/etc/chrony/sources.d/ubuntu-hardening.sources` — свои серверы (`NTP_SERVERS`) и `time.cloudflare.com` с NTS (`NTP_ADD_NTS`);
- `/etc/chrony/conf.d/ubuntu-hardening.conf` — `minsources`, `maxdistance 1.5`, `bindcmdaddress` только localhost.

Штатные пулы Ubuntu, `rtcsync`, `makestep`, `leapsectz` и `sourcedir /run/chrony-dhcp` (NTP провайдера по DHCP) остаются из файла пакета; на новых выпусках Ubuntu штатные источники уже аутентифицированы NTS. `NTP_REPLACE_DEFAULTS=yes` комментирует штатные `pool`/`server` и отключает чужие `*.sources` — тогда используются только ваши серверы, а `minsources` становится `1`, если источник один. `systemd-timesyncd` отключается.

### 2. SSH-ключ администратора

| Вариант | Где приватный ключ |
|---|---|
| **Ключи root** (по умолчанию, если есть) | Только у вас — вы уже входите с ними. Берутся из `/root/.ssh/authorized_keys`; опции перед ключом (например, `command="echo 'Please login as the user …'"` в cloud-образах) отбрасываются |
| **Свой публичный ключ** | Только у вас. Строка проверяется `ssh-keygen -l` |
| Сгенерировать ed25519 / ecdsa-521 | На сервере (с паролем, `-a 100`); скачать и удалить в секции 20. В режиме `--yes` недоступно |

RSA короче 3072 бит отклоняется во всех вариантах (неподходящие ключи root показываются с причиной).

```bash
# у себя — для варианта «свой ключ»
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/admin_ssh_key
cat ~/.ssh/admin_ssh_key.pub        # эту строку вставить в диалог или SSH_PUBKEY
```

**Сгенерированный приватный ключ выводится напрямую в терминал (`/dev/tty`), мимо лога выполнения.** Пока root ещё может входить по SSH, его можно скачать: `scp root@<IP>:/root/admin_ssh_key ./admin_ssh_key`.

### 3. Создание пользователя-администратора

Имя: строчные латинские буквы, цифры, `_` и `-`. Лучше неочевидное: `admin` перебирают первым, а в sudoers Ubuntu до сих пор есть строка `%admin ALL=(ALL) ALL`.

```bash
useradd -m -s /bin/bash <user>      # с -g <user>, если такая группа уже существует
usermod -aG sudo <user>             # выполняется всегда, и при повторном запуске
```

- **политика паролей записывается до `passwd`** (drop-in `pwquality.conf.d/50-ubuntu-hardening.conf`, см. [секцию 16](#16-пароли-logindefs-faillock)) с `enforce_for_root`;
- пароль нужен только для sudo. Новому пользователю он задаётся обязательно (в цикле — ошибки ввода не роняют скрипт); при повторном запуске — только если вы согласились его сменить; в `--yes` — из `ADMIN_PASSWORD_HASH`;
- **`authorized_keys` не пересортировывается**: ключ дописывается, только если его там нет. Ключи, поставленные прошлым прогоном и больше не выбранные, удаляются; ключи, добавленные вручную, не трогаются. Шаг останавливается, если в итоге нет ни одного действующего ключа;
- домашний каталог берётся из `getent passwd`, а не из `/home/<user>`;
- параметры прогона сохраняются в `/etc/ubuntu_hardening.conf` (`600`, читается построчно, не через `source`): администратор и порт — только после того, как они реально применены.

### 4. Настройка SSH

Файл: `/etc/ssh/sshd_config`. Исходный файл сохраняется в каталог прогона (`--rollback`). Шаг останавливается до любых изменений, если у администратора нет действующего ключа. Новый конфиг сначала пишется во временный файл и проверяется `sshd -t -f`; на место он попадает, только если проверка прошла.

**Права на каталог и файлы** (CIS 5.1.1–5.1.2):

```
/etc/ssh                    755   (700 ломало ssh-КЛИЕНТ для обычных пользователей —
                                   им нужен доступ к /etc/ssh/ssh_config)
/etc/ssh/sshd_config        600
ssh_host_*_key              600
ssh_host_*_key.pub          644
```

**Ключевые параметры:**

| Параметр | Значение | CIS | Обоснование |
|---|---|---|---|
| `Port` | выбранный | — | `22` или 1024–65535. Нестандартный порт лишь снижает шум сканеров в логах; защиту дают ключи, fail2ban и UFW. Порты 1–1023, кроме 22, запрещены: их могут занять другие службы |
| `AddressFamily` | `any` | — | Переменная `SSH_ADDRESS_FAMILY`; `inet` опасен на IPv6-only VPS |
| `PermitRootLogin` | `no` | 5.1.20 | Прямой вход root запрещён |
| `PasswordAuthentication` | `no` | — | Только ключевая аутентификация |
| `AuthenticationMethods` | `publickey` | — | Явное требование ключа |
| `HostbasedAuthentication` / `IgnoreRhosts` | `no` / `yes` | 5.1.9–5.1.10 | Доверие по хосту и `.rhosts` |
| `PermitUserEnvironment` | `no` | 5.1.11 | `~/.ssh/environment` мог бы подменить `LD_PRELOAD` |
| `PermitEmptyPasswords` | `no` | 5.1.19 | |
| `LoginGraceTime` | `30` | 5.1.13 | `0` означало бы «без лимита» — баг оригинальной конфигурации |
| `MaxAuthTries` | `3` | 5.1.16 | Максимум попыток на соединение |
| `MaxSessions` | `5` | 5.1.17 | |
| `MaxStartups` | `5:30:20` | 5.1.18 | Защита от медленных атак на handshake |
| `ClientAliveInterval` / `CountMax` | `300` / `2` | 5.1.7 | Разрыв при 10 мин простоя |
| `AllowUsers` | `<user>` | 5.1.4 | Только указанный пользователь |
| `AllowTcpForwarding` | `no` | 5.1.5 | Туннели обходят firewall; `TCP_FORWARDING` |
| `AllowAgentForwarding` | `no` | 5.1.5 | Root на сервере мог бы пользоваться вашим ssh-agent, пока вы подключены; `AGENT_FORWARDING` |
| `PermitTunnel` | `no` | — | tun-устройства через SSH |
| `GatewayPorts` / `X11Forwarding` | `no` | 5.1.22 | |
| `LogLevel` | `VERBOSE` | 5.1.14 | Fingerprint ключа в каждой записи лога |
| `Banner` | `/etc/ssh/my_banner` | 5.1.3 | Юридическое предупреждение |
| `DebianBanner` / `VersionAddendum` | `no` / `none` | — | Скрыть версию ОС от сканеров |
| `Subsystem sftp` | `internal-sftp` | — | Встроенный SFTP: без отдельного бинарника, работает в chroot |

Устаревшие `Protocol 2` и `ChallengeResponseAuthentication` убраны: в OpenSSH 9.x они игнорируются или являются синонимами.

**Криптография** (CIS 5.1.6 / 5.1.12 / 5.1.15) — только современные алгоритмы:

```
HostKeyAlgorithms : ssh-ed25519, ecdsa-sha2-nistp521, rsa-sha2-512/256
KexAlgorithms     : mlkem768x25519-sha256, sntrup761x25519-sha512(@openssh.com),
                    curve25519-sha256, ecdh-sha2-nistp521
                    — только те, что поддерживает установленный OpenSSH (ssh -Q kex)
Ciphers           : chacha20-poly1305, aes256-gcm, aes128-gcm
MACs              : hmac-sha2-512-etm, hmac-sha2-256-etm
```

**Постквантовый обмен ключами.** Гибриды `sntrup761x25519` (OpenSSH 9.0+, Ubuntu 24.04) и `mlkem768x25519` (OpenSSH 9.9+, Ubuntu 26.04) включены в OpenSSH по умолчанию и защищают записанный сегодня трафик от расшифровки в будущем. v2 их отключала, оставляя только `curve25519`; с v3 скрипт ставит их первыми, если версия OpenSSH их знает.

**Drop-in файлы.** В конце `sshd_config` стоит `Include /etc/ssh/sshd_config.d/*.conf`. sshd использует первое встреченное значение директивы, поэтому наши настройки выше Include не перебиваются drop-in файлами (например, `50-cloud-init.conf` с `PasswordAuthentication yes`), а drop-in могут добавлять только то, что мы не задали.

**Порядок применения — важен, здесь были главные баги прошлых версий:**

1. **Drop-in файлы**: `Port` и `ListenAddress`, в отличие от остальных директив, **накапливаются** — drop-in с ними открыл бы второй порт. Такие файлы перемещаются в каталог прогона (`/var/backups/ubuntu_hardening/<метка>/moved/`) и возвращаются при `--rollback`;
2. `sshd -t -f <временный файл>` — валидация до установки; затем `sshd -T` проверяет итоговую конфигурацию: порт ровно один, `PasswordAuthentication no` (иначе скрипт останавливается);
3. **UFW уже активен** (бывает в образах провайдеров) — новый порт открывается `ufw limit` **до** перезапуска sshd, иначе контрольная точка не прошла бы;
4. **Отключение `ssh.socket`**: Ubuntu 22.10+ по умолчанию запускает SSH через socket-активацию systemd, при которой порт задаёт сокет, а `Port` из `sshd_config` **игнорируется**. Это и было истинной причиной проблемы «порт не поменялся». Скрипт переключает на классический `ssh.service`;
5. Имя службы (`ssh`/`sshd`) определяется по наличию юнита;
6. Рестарт и подтверждение порта через `ss -Htln "sport = :<порт>"`;
7. **Контрольная точка**: скрипт останавливается и требует подтвердить вход под администратором из нового терминала. Ответ `n` прерывает выполнение — root остаётся разблокированным, можно чинить и перезапускать. В режиме `--yes` вместо человека — автоматическая проверка (см. [Неинтерактивный режим](#неинтерактивный-режим)).

### 5. Блокировка root

```bash
passwd -l root
```

Если шаг `ssh` в этот прогон не входит (`--only root`), перед блокировкой выполняется контрольная точка входа.

Дополнительно `su` ограничивается членами группы `sudo` через `pam_wheel.so group=sudo` в `/etc/pam.d/su` (CIS 5.2.7) — непривилегированный пользователь не сможет даже пытаться подобрать пароль root через `su`.

> **Исправлено в v3.** В Ubuntu строка в `/etc/pam.d/su` закомментирована как `# auth       required   pam_wheel.so` — с пробелом после `#`. Проверка v2 (`^#auth`) её не находила, а поиск подстроки `pam_wheel.so` срабатывал на сам комментарий, поэтому файл не менялся. Теперь строка раскомментируется с `group=sudo` (без этой опции pam_wheel проверял бы группу root); если строки нет — вставляется перед `@include common-auth`. Перед изменением — резервная копия, после — проверка результата.

### 6. Брандмауэр UFW

**Перед сбросом правил** скрипт показывает слушающие TCP- и UDP-порты (`ss -tlnp`, `ss -ulnp`) и предлагает перечислить дополнительные — раньше `ufw --force reset` молча закрывал порты уже работающих сервисов (веб-сервер и т.п.).

Формат ввода: `80 443` (TCP), `443/udp 51820/udp` (HTTP/3, WireGuard), `8000:8100/tcp` (диапазон). Некорректные значения пропускаются; правило, отклонённое UFW, не прерывает скрипт.

```bash
ufw default deny incoming      # CIS 4.2.7
ufw default allow outgoing
ufw default deny routed
ufw limit <PORT>/tcp           # rate-limit iptables: 6 попыток за 30 сек → блок
ufw allow <port>[/tcp|udp]     # порты, указанные пользователем (с валидацией)
```

`ufw limit` вместо `ufw allow` для SSH — встроенная защита от брутфорса, работающая ещё до Fail2ban. Исходные правила UFW сохраняются в каталог прогона, `--rollback` их возвращает.

**Docker.** Docker публикует порты (`-p 5432:5432`) через собственные цепочки iptables, которые срабатывают раньше правил UFW: «закрытый» UFW-ом порт контейнера доступен из интернета. При найденном Docker (`DOCKER_UFW_FIX=auto`) в `/etc/ufw/after.rules` добавляется цепочка `DOCKER-USER`: трафик из частных сетей и ответы проходят, новые входящие соединения извне к контейнерам блокируются и логируются (`[UFW DOCKER BLOCK]`). Открытыми остаются порты из `DOCKER_ALLOW_PORTS` — по умолчанию те, что уже опубликованы на `0.0.0.0`/`::`, чтобы работающие сервисы не упали:

```bash
ufw route allow proto tcp from any to any port 80   # открыть порт контейнера
```

Важно: указывается порт **контейнера** — DOCKER-USER видит пакет после DNAT, поэтому для `-p 8080:80` это `80`. Альтернатива без правил — публиковать порты только на localhost (`-p 127.0.0.1:5432:5432`) и выводить наружу через reverse proxy. Блок проверен `iptables-restore --test`; правила IPv6 для Docker не добавляются (IPv6 в Docker выключен по умолчанию).

> 💡 **VPS-специфика:** Hetzner / DigitalOcean / Vultr предоставляют собственный firewall в панели — продублируйте правила и там. Это защита в глубину: UFW внутри гостя, firewall провайдера снаружи.

### 7. Fail2ban

Файл: `/etc/fail2ban/jail.local`

| Параметр | Значение | Комментарий |
|---|---|---|
| `backend` | `systemd` | чтение journald напрямую, не зависит от файлов логов |
| `banaction` | `ufw` | баны через тот же firewall |
| `port` | выбранный SSH-порт | подставляется автоматически |
| `maxretry` / `bantime` (sshd) | `3` / `24h` | |
| `findtime` | `10m` | окно подсчёта попыток |
| `mode` (sshd) | `aggressive` | ловит перебор ключами и обрывы до аутентификации (сканеры) |

### 8. Защита cron

```bash
chown root:root /etc/crontab /etc/cron.{hourly,daily,weekly,monthly,d}/
chmod og-rwx    /etc/crontab /etc/cron.{hourly,daily,weekly,monthly,d}/
```

Создаются `/etc/cron.allow` и `/etc/at.allow` (600), содержащие только `root`; файлы `cron.deny` / `at.deny` удаляются (CIS 2.4.1). При наличии обоих файлов `allow` имеет приоритет, но явное удаление `deny` исключает неоднозначность. Обработка `at` — только если он установлен.

### 9. Защита разделов

Файл: `/etc/fstab`. CIS 1.1.2.x.

| Раздел | Флаги | От чего защищает |
|---|---|---|
| `/tmp` | tmpfs `nosuid,nodev,noexec,size=<¼ RAM>` или bind на себя с теми же флагами | Выполнение залитых файлов из /tmp |
| `/dev/shm` | `nosuid,nodev,noexec` | Исполнение из разделяемой памяти |
| `/var/tmp` | bind на себя `nosuid,nodev,noexec` | То же, содержимое переживает reboot |
| `/home` | `nosuid,nodev` + `noexec` при `HOME_NOEXEC=yes` | Исполнение из домашних каталогов |
| `/proc` | `hidepid=invisible,gid=proc` при `HIDEPID=yes` | Просмотр чужих процессов и их аргументов |

- **`/tmp` и объём RAM** (`TMP_MODE=auto`): при RAM ≥ 2 ГБ — tmpfs размером в четверть RAM (256 МБ – 2 ГБ); при меньшей памяти tmpfs отнимал бы её у сервисов, поэтому `/tmp` остаётся на диске, а флаги даёт bind-монтирование. Смена типа (tmpfs ↔ диск) применяется после перезагрузки;
- **`/var/tmp`** по FHS переживает перезагрузку — bind каталога на себя;
- записи fstab заменяются по точке монтирования (поле 2), комментарии не затрагиваются;
- **`/home` не отдельный раздел** (типично для VPS) — bind `/home /home none bind,…`; `remount-home.service` из v2 удаляется;
- ⚠️ `noexec` на `/home` ломает `~/.local/bin`, VS Code Remote, rustup, nvm, pipx. Если это нужно — `HOME_NOEXEC=no`;
- **`hidepid`** применяется после перезагрузки; `systemd-logind` и `polkitd` добавляются в группу `proc`. Агентам мониторинга, которым нужны все процессы, тоже добавьте эту группу;
- **noexec `/tmp` и apt**: временный каталог apt перенесён в `/var/lib/apt/tmp` (`99tempdir`) — иначе ночные unattended-upgrades могли падать с `Permission denied`.

### 10. Параметры ядра (sysctl)

Файл: `/etc/sysctl.d/99-hardening.conf`, применение через `sysctl --system`. `--audit` сверяет каждый параметр файла с текущим значением ядра — так виден дрейф (например, если параметр перебил другой файл или пакет).

**Сеть** (CIS 3.3.x):

| Параметр | Значение | Защита от / комментарий |
|---|---|---|
| `rp_filter` (all/default) | `1`, при нескольких интерфейсах `2` | IP-спуфинга; строгий режим ломает асимметричную маршрутизацию |
| `accept_source_route` (v4+v6) | `0` | пакетов с маршрутом источника |
| `ip_forward` | `0`, **или `1` при `IP_FORWARD`** | см. ниже |
| `tcp_syncookies`, `synack_retries=2`, `max_syn_backlog=4096` | | SYN-flood |
| `accept_redirects`, `secure_redirects`, `send_redirects` | `0` | ICMP MITM |
| `icmp_echo_ignore_broadcasts`, `icmp_ignore_bogus_error_responses` | `1` | Smurf-атак |
| `log_martians` | `1` (`LOG_MARTIANS=no` — не писать) | в некоторых сетях провайдеров очень шумно |
| `accept_ra` (v6) | `0` **только без глобального IPv6** | см. ниже |
| `tcp_rfc1337` | `1` | TIME-WAIT assassination |

**Форвардинг и контейнеры.** Docker включает `ip_forward` при старте, но следующий `sysctl --system` (его запускают обновления пакетов) с `ip_forward = 0` выключал его обратно, и контейнеры теряли сеть. `IP_FORWARD=auto` включает форвардинг IPv4, если найдены Docker, Podman, LXD или конфигурация WireGuard; `yes`/`no` — принудительно.

**Router Advertisement.** У многих провайдеров IPv6-маршрут по умолчанию приходит через RA; `accept_ra = 0` на таких серверах (ifupdown, NetworkManager) отрезал IPv6. `IPV6_ACCEPT_RA=auto` запрещает RA, только если у сервера нет глобального IPv6-адреса.

**Ядро:**

| Параметр | Значение | Описание |
|---|---|---|
| `kernel.yama.ptrace_scope` | `1` | ptrace только от родителя; `2` сломал бы `strace`/`gdb` |
| `kernel.dmesg_restrict`, `kernel.kptr_restrict` | `1`, `2` | dmesg и адреса ядра скрыты |
| `kernel.sysrq` | `0` | есть консоль провайдера |
| `kernel.randomize_va_space` | `2` | ASLR |
| `fs.suid_dumpable`, `kernel.core_pattern` | `0`, `\|/bin/false` | см. секцию 12 |
| `fs.protected_{hardlinks,symlinks,fifos,regular}` | `1`/`1`/`2`/`2` | атаки через ссылки и sticky-каталоги |
| `kernel.kexec_load_disabled` | `1` | подмена ядра без перезагрузки |
| `kernel.unprivileged_bpf_disabled`, `net.core.bpf_jit_harden` | `1`, `2` | eBPF |
| `dev.tty.ldisc_autoload`, `vm.unprivileged_userfaultfd` | `0` | классы эксплойтов ядра |
| `kernel.perf_event_paranoid` | `3` — **только если сейчас ниже** | ядра Ubuntu поддерживают уровень `4` и обычно уже так настроены; запись `3` ослабила бы его |

**User namespaces** — `unprivileged_userns_clone = 0` и `apparmor_restrict_unprivileged_userns = 1` пишутся только если параметр есть в ядре. ⚠️ Это ломает **rootless Docker/Podman** — закомментируйте строки и выполните `sysctl --system`.

### 11. Blacklist модулей ядра

Файл: `/etc/modprobe.d/hardening-blacklist.conf`; каждый модуль — `blacklist` + `install <mod> /bin/false`.

- **файловые системы** (CIS 1.1.1.x): `cramfs freevxfs jffs2 hfs hfsplus udf`, а также `squashfs` — **только если не установлен snapd** (snap монтирует squashfs);
- **сетевые протоколы с историей CVE** (CIS 3.2.x): `dccp sctp rds tipc`, а также редкие семейства `ax25 netrom rose x25 appletalk ipx can atm` и line discipline `n_hdlc`.

Загруженные модули из списка выгружаются сразу (если не заняты). initramfs пересобирается подходящим инструментом (`update-initramfs` или `dracut` на 26.04), ошибка выводится.

> **VPS-специфика:** USB-storage, Firewire и virtio не трогаются — на виртуалке первых нет, а вторые нужны для загрузки.

**Параметры загрузки ядра** (`KERNEL_CMDLINE_HARDENING=yes`): `/etc/default/grub.d/99-ubuntu-hardening.cfg` добавляет `slab_nomerge init_on_alloc=1 page_alloc.shuffle=1 vsyscall=none`, затем `update-grub`. Действует после перезагрузки; `init_on_alloc=1` стоит единицы процентов производительности, `vsyscall=none` ломает очень старые статически собранные бинарники.

| Уровень | Файл | Покрывает |
|---|---|---|
| `hard core 0` | `/etc/security/limits.d/99-ubuntu-hardening-core.conf` | PAM-сессии |

### 13. Auditd

**Повторный запуск при immutable-правилах** (`auditctl -s` → `enabled 2`): файлы конфигурации и правил записываются, а загрузка и рестарт auditd пропускаются с предупреждением — новые правила начнут действовать после перезагрузки. (v3 пропускала секцию целиком, и изменения не доходили до файлов.)

**`/etc/audit/auditd.conf`** — лимиты рассчитаны в секции 0:

```
max_log_file        = <квота ÷ 5> МБ        num_logs = 5
max_log_file_action = ROTATE                 log_format = ENRICHED
space_left_action   = SYSLOG                 admin_space_left_action = ROTATE
disk_full_action    = ROTATE  ← не halt/single: VPS без консоли ушёл бы в офлайн
flush = INCREMENTAL_ASYNC     freq = 50
```

Устаревшие `dispatcher = /sbin/audispd` и `disp_qos` **отсутствуют** — они удалены в auditd 3.x (Ubuntu 22.04+), с ними демон мог не стартовать.

**Файлы правил** (`augenrules` читает их в порядке `ls -v` и для `-b`, `-f`, `-e` оставляет **последнее** значение):

| Файл | Содержимое |
|---|---|
| `70-privileged.rules` | запуск каждой SUID/SGID-программы, найденной на сервере (`find / -xdev -perm /6000`), ключ `privileged` (CIS 6.2.3.6) |
| `99-hardening.rules` | основные правила (таблица ниже) |
| `audit.rules` | файл пакета — его `-b 8192` в v3 перебивал расчётный backlog |
| `zz-hardening-finalize.rules` | `-b <backlog>`, `-f 1`, `-e 2` — читается последним, поэтому значения скрипта побеждают |

**Правила `99-hardening.rules`:**

| Категория | Что отслеживается | Ключ | CIS |
|---|---|---|---|
| Идентификация | `/etc/passwd`, `shadow`, `group`, `gshadow`, `security/opasswd` | `identity` | 6.2.3.8 |
| Привилегии | `/etc/sudoers`, `/etc/sudoers.d/` | `sudoers` | 6.2.3.1 |
| Журнал sudo | `/var/log/sudo.log` | `sudo_log` | 6.2.3.3 |
| PAM | `/etc/pam.d/`, `/etc/security/`, `login.defs` | `pam` | — |
| SSH | `sshd_config`, `sshd_config.d/`, `~<user>/.ssh/`, `/root/.ssh/` | `sshd_config`, `ssh_keys` | — |
| Входы и сессии | `lastlog`, `faillog`, `faillock`, `utmp`, `wtmp`, `btmp` | `logins`, `session` | 6.2.3.12–13 |
| Cron | все cron-каталоги + `/var/spool/cron/` | `cron` | — |
| Автозагрузка | `/etc/systemd/system/`, `ld.so.preload`, `ld.so.conf.d/` | `systemd`, `preload` | — |
| Время | `adjtimex`/`settimeofday`/`clock_settime` от пользователей, `/etc/localtime` | `time_change` | 6.2.3.4 |
| Хост и сеть | `sethostname`/`setdomainname`, `hosts`, `hostname`, `netplan/`, `resolv.conf` | `system_locale` | 6.2.3.5 |
| AppArmor | `/etc/apparmor/`, `/etc/apparmor.d/` | `mac_policy` | 6.2.3.14 |
| Монтирование | `mount`/`umount2` от пользователей | `mounts` | 6.2.3.10 |
| Права файлов | `chmod`/`chown`, `setxattr`/`removexattr` и варианты, **b64 + b32**, `fchmodat2`, фильтр `auid>=1000` | `file_perm` | 6.2.3.9 |
| Удаление | `unlink`/`unlinkat`/`rename`/`renameat` (b64+b32), `renameat2` | `delete` | 6.2.3.13 |
| Отказ в доступе | `open`/`openat`/`creat`/`truncate` (b64+b32), `openat2`/`open_by_handle_at` с `EACCES`/`EPERM` | `access` | 6.2.3.7 |
| Повышение привилегий | `setuid`/`setgid` (b64+b32) от пользователей; `execve` при `euid=0` | `priv_esc`, `priv_exec` | 6.2.3.6 |
| Модули ядра | `/usr/bin/kmod` + syscalls `*_module` (b64+b32) | `kernel_modules` | 6.2.3.19 |
| Сеть | **только `bind`** реальных пользователей (b64+b32) | `net_bind` | — |
| Загрузчик и ядро | `/boot/`, `kexec_load`/`kexec_file_load` (b64), `kexec_load` (b32) | `boot`, `kexec` | — |

Принципиальные решения:

- **правила `socket`/`connect` намеренно отсутствуют** — аудит каждого сетевого вызова генерировал тысячи событий в секунду и был первопричиной ошибки `audit: backlog limit exceeded`; увеличение буфера лечило симптом. Новый слушающий сокет (`bind`) — редкое и действительно значимое событие, он оставлен;
- **дублирование b64 + b32**: без правил для `arch=b32` аудит тривиально обходился 32-битными syscalls;
- фильтр `-F auid>=1000 -F auid!=unset` отсекает шум системных демонов, оставляя действия реальных пользователей; в v3 он добавлен и к `setuid`/`setgid` (их постоянно вызывают cron, sshd, systemd) и к правилам времени (chronyd подстраивает часы непрерывно);
- **`/usr/bin/kmod` вместо `/sbin/insmod`, `rmmod`, `modprobe`**: это симлинки на kmod, и наблюдение `-p x` за симлинком не срабатывает при запуске;
- **новые syscalls — отдельными правилами**: если `auditctl` не знает syscall (`fchmodat2` на 22.04), отклоняется всё правило; отдельное правило теряет только себя, а не, например, аудит `chmod`;
- `-i` в начале правил: если какого-то syscall или пути нет в этой версии ядра/ОС (например, b32 без IA32-эмуляции), остальные правила всё равно загружаются;
- `-b <backlog>` — рассчитан из RAM и стоит в `zz-hardening-finalize.rules`, чтобы его не перебил `audit.rules` дистрибутива; `--backlog_wait_time` убран (значение `1` из старой версии *уменьшало* ожидание и увеличивало потери — комментарий был неверным);
- `-f 1` — при сбое аудита писать в syslog, **не** паника ядра (`-f 2`): на VPS без физической консоли паника означает недоступный сервер;
- `-e 2` в конце — правила **неизменяемы до перезагрузки**: злоумышленник не отключит аудит без reboot, который сам оставит след.

**Ротация:** только средствами auditd. Отдельный `/etc/logrotate.d/audit` **не создаётся и удаляется, если был** — auditd держит файл открытым и ротирует сам; параллельный logrotate с рестартом демона давал двойную ротацию и разрывы аудита.

Просмотр событий:

```bash
ausearch -k identity   | tail -20   # изменения passwd/shadow
ausearch -k sudoers    | tail -20   # изменения sudoers
ausearch -k ssh_keys   | tail -20   # изменения SSH-ключей
ausearch -k priv_exec  | tail -20   # команды от root реальными пользователями
ausearch -k net_bind   | tail -20   # новые слушающие сокеты
ausearch -k pam        | tail -20   # изменения PAM
ausearch -k access     | tail -20   # отказы в доступе к файлам
ausearch -k privileged | tail -20   # запуск SUID/SGID-программ
ausearch -k delete     | tail -20   # удаление файлов пользователями
aureport --summary                  # сводка
auditctl -s                         # backlog, lost, enabled
```

### 14. AppArmor

`apparmor`/`apparmor-utils` доустанавливаются при отсутствии (проверка через `dpkg -s`), служба включается, выводится отчёт: сколько профилей загружено и сколько в режиме `complain`.

**Изменено в v3.** v2 переводила в `enforce` все файлы `/etc/apparmor.d/`. Но часть профилей дистрибутив держит в `complain` или с `flags=(unconfined)` намеренно — на 24.04 это десятки профилей, разрешающих программам user namespaces, — и принудительный enforce ломал эти программы. Теперь по умолчанию — только отчёт; переводите профили выборочно:

```bash
aa-status | sed -n '/complain mode/,/^[0-9]/p'   # что в complain
aa-enforce /etc/apparmor.d/<профиль>             # перевести один
```

`APPARMOR_ENFORCE_ALL="yes"` в начале скрипта переводит в enforce все complain-профили, кроме помеченных `unconfined` (CIS 1.3.1.4).

### 15. Настройка sudo

Файл: `/etc/sudoers.d/99-hardening` (права 440).

**Проверка до установки (исправлено в v3).** Root к этому моменту заблокирован, а битый файл в `sudoers.d` ломает sudo целиком — это полная потеря доступа, остаётся только VNC и recovery. Поэтому файл сначала пишется во временный, проверяется `visudo -c -f`, и только потом ставится на место; затем `visudo -c` проверяет sudoers целиком, и при ошибке наш файл убирается. Если проверка не прошла — sudo продолжает работать как раньше.

| Настройка | Значение | Назначение |
|---|---|---|
| `timestamp_timeout=5` | 5 минут | сессия sudo истекает быстро |
| `use_pty` | — | команда в отдельном псевдотерминале: фоновый процесс не перехватит ввод |
| `secure_path` | фиксированный | защита от подмены системных утилит через PATH |

`!visiblepw` убран: это значение по умолчанию. В Ubuntu 25.10+ / 26.04 вместо sudo используется **sudo-rs**, который поддерживает не все `Defaults`, — скрипт использует только общие для обоих.

**Логирование** — через rsyslog (`/etc/rsyslog.d/50-sudo.conf`): события sudo копируются в `/var/log/sudo.log` и **остаются в `auth.log`**. Файл принадлежит `syslog:adm` с правами `640`: rsyslog в Ubuntu пишет от имени `syslog`, а созданный в v3 файл `root:root 600` он открыть не мог, и отдельный лог оставался пустым. Ротация — `/etc/logrotate.d/sudo-log` (еженедельно, 12 архивов). Формат записи:

```
Jul 14 03:12:44 server sudo: admin : TTY=pts/0 ; PWD=/home/admin ; USER=root ; COMMAND=/bin/bash
```

Опции `log_output`, `logfile`, `requiretty` **сознательно не используются**: первые две требуют I/O-плагин sudo, не входящий в пакет Ubuntu, третья удалена из sudo 1.9.x — с ними `sudo -i` падал с `unknown setting`.

### 16. Пароли, login.defs, faillock

**pwquality** — drop-in `/etc/security/pwquality.conf.d/50-ubuntu-hardening.conf` (CIS 5.3.3.2.x); `pwquality.conf` из пакета не трогается (перезаписанный v3 возвращается к умолчаниям). Записывается в секции 3 до задания пароля, здесь — повторно, для `--only accounts`.

| Параметр | Значение | Смысл |
|---|---|---|
| `minlen` | `16` | минимальная длина |
| `dcredit`/`ucredit`/`lcredit`/`ocredit` | `-1` (при `PASSWORD_CLASSES=yes`) | по одной цифре / заглавной / строчной / спецсимволу |
| `maxrepeat`, `dictcheck`, `usercheck`, `gecoscheck` | `3`, `1`, `1`, `1` | повторы, словарь, имя пользователя, GECOS |
| `enforce_for_root` | — | политика действует и когда пароль задаёт root |

`PASSWORD_CLASSES=no` убирает требования к классам символов и оставляет длину 16+ и словарную проверку — так рекомендует NIST SP 800-63B; по умолчанию сохранено требование CIS.

**`/etc/login.defs`:** `UMASK 027` (новые файлы не читаются «прочими»), `PASS_MAX_DAYS 365` (`PASSWORD_MAX_DAYS`), `PASS_MIN_DAYS 1`, `PASS_WARN_AGE 7`, на 24.04+ — `ENCRYPT_METHOD YESCRYPT` (shadow 4.8 в 22.04 его не знает; `passwd` там и так пишет yescrypt через PAM). Срок пароля применяется и к администратору (`chage`): по истечении sudo попросит сменить пароль.

**faillock** (`ENABLE_FAILLOCK=yes`, по умолчанию выключен): профили `pam-auth-update` `ubuntu-hardening-faillock*` и `/etc/security/faillock.conf` — 5 неверных паролей за 15 минут блокируют `sudo`/`su` пользователя на 15 минут; root не блокируется. SSH это не затрагивает (вход только по ключу). После включения скрипт проверяет порядок модулей в `common-auth` (`preauth` → `pam_unix` → `authfail`) и при отклонении откатывает изменения — ошибка в PAM при заблокированном root означала бы потерю доступа к sudo. Поведение проверено `pamtester` на Ubuntu 24.04. Выключен по умолчанию, потому что ошибиться паролем 5 раз при заблокированном root — это 15 минут без sudo. Снять блокировку: `faillock --user <имя> --reset` (из-под root через консоль провайдера или после истечения срока).

### 17. Права на системные файлы

```bash
chown root:shadow /etc/shadow /etc/gshadow
chmod 640 /etc/shadow /etc/gshadow      # CIS 7.1.3–7.1.4
chmod 644 /etc/passwd /etc/group        # CIS 7.1.1–7.1.2
chmod 700 /boot
```

`640 root:shadow` — как в Ubuntu и допускается CIS. При `600` (v2) setgid-утилита `unix_chkpwd` не может читать `/etc/shadow` и проверять пароли для непривилегированных процессов.

SUID снимается с редко используемых утилит `chfn`, `chsh`, `newgrp` через `dpkg-statoverride` — простой `chmod u-s` возвращался при следующем обновлении пакета `passwd`. Снять: `dpkg-statoverride --remove <файл> && chmod u+s <файл>` (или `--rollback`).

> **Изменение v2:** симлинк `~root/.bash_history → /dev/null` **убран**. Отключение истории — антифорензика: при инциденте она помогает атакующему скрыть следы больше, чем защищает владельца. Команды с правами root аудирует auditd (ключ `priv_exec`) — этот журнал, в отличие от истории shell, защищён immutable-правилами.

### 19. Автоматические обновления

**`/etc/apt/apt.conf.d/52unattended-upgrades-hardening`** — собственный файл вместо перезаписи `50unattended-upgrades` из пакета (в v2 при обновлении пакета терялись новые умолчания). Директива `#clear` заменяет списки целиком — без неё apt **дописал** бы наши значения к стандартным.

Разрешённые источники — `-security`, ESM Apps/Infra (Ubuntu Pro), `-updates` (многие исправления безопасности приходят именно через `-updates`, а не `-security`).

Исключения — пакеты с данными и оркестрация, обновление которых должно быть ручным и контролируемым. Записи — регулярные выражения, которые unattended-upgrades сравнивает **от начала имени** (`re.match`): `mysql` задерживает `mysql-server*`, но не `libmysqlclient*`; `postgresql` задерживает и клиент `postgresql-client-*`:

```
docker  containerd  kube  postgresql  mysql  mariadb  redis  mongodb
```

**nginx и apache больше не исключены**: это самые открытые наружу сервисы, их security-исправления важнее короткого перезапуска.

**needrestart** (`/etc/needrestart/conf.d/50-hardening.conf`, режим `a`): после обновления библиотек сервисы перезапускаются автоматически — иначе уязвимая версия остаётся загруженной в память до перезагрузки.

| Параметр | Значение | Причина |
|---|---|---|
| `AutoFixInterruptedDpkg` | `true` | исправлять прерванные установки |
| `MinimalSteps` | `true` | атомарные шаги — безопасное прерывание |
| `Remove-Unused-Dependencies` | `true` | без orphan-пакетов |
| `Automatic-Reboot` | `false` | неожиданный reboot продакшн-VPS недопустим; необходимость видна по `/var/run/reboot-required` |
| `Mail` / `MailOnlyOnError` | `root` / `true` | письмо только при ошибках; без MTA оно никуда не уйдёт — смотрите `/var/log/unattended-upgrades/` и `--audit` (число ожидающих пакетов, нужна ли перезагрузка) |

**Расписание** — systemd drop-in (не перезапись unit-файла, чтобы обновления пакетов не затирали настройку):

```
/etc/systemd/system/apt-daily.timer.d/override.conf           →  03:00 ± 10 мин
/etc/systemd/system/apt-daily-upgrade.timer.d/override.conf   →  03:30 ± 10 мин
```

Перед новым `OnCalendar` дефолтные значения сбрасываются пустыми строками — иначе systemd объединяет расписания и таймер срабатывает по обоим. `RandomizedDelaySec=10m` — чтобы VPS одного провайдера не стучались в репозитории одновременно. Проверка: `systemctl list-timers apt-daily*`.

### 19.1 Журнал systemd и пересылка логов

`/etc/systemd/journald.conf.d/50-ubuntu-hardening.conf`: `Storage=persistent` (журнал переживает перезагрузку — без этого история входов теряется при reboot), `Compress=yes`, `SystemMaxUse` — та же квота, что для auditd (10% свободного места, 50 МБ – 2 ГБ), `SystemKeepFree` — половина квоты.

**Пересылка** (`REMOTE_SYSLOG=host:port`): злоумышленник с root на сервере может стереть локальные журналы, копия на другом хосте остаётся. rsyslog пересылает все сообщения по TCP с дисковой очередью (256 МБ, переживает перезагрузку и недоступность приёмника); плагин auditd `syslog` включается, и события аудита уходят туда же, не дублируясь в `/var/log/syslog`. ⚠️ Канал не шифруется — используйте VPN/WireGuard или настройте TLS (`gtls`) вручную.

### 19.2 Контроль целостности (AIDE)

`ENABLE_AIDE=yes` (по умолчанию выключено, CIS 6.1): устанавливаются `aide` и `aide-common`, строится база (`aideinit`, несколько минут и заметная нагрузка на диск), включается ежедневная проверка (`dailyaidecheck.timer` или `cron.daily`). После обновлений пакетов база обновляется `aideinit -y -f`; без этого отчёты будут шумными.

### 19.5. Шифрование LUKS (необязательно)

Скрипт показывает `--luks status` и предлагает меню: отдельный диск, файл-контейнер, защита swap, SSH-разблокировка root, шифрование корня, данные Docker. `Enter` — пропустить; в режиме `--yes` шаг не выполняется. Секция стоит до шага 20, чтобы dropbear в initramfs получил `authorized_keys` администратора.

Режим выполняется в подоболочке: ошибка внутри него не прерывает харденинг — скрипт сообщает код и идёт дальше. То же самое позже: `bash ubuntu_hardening.sh --luks <режим>`. Подробности — в разделе [Шифрование LUKS](#шифрование-luks-режим---luks).

### 20. Приватный ключ, лишние службы, итог

**Логи v2 с ключом** — файлы `/root/hardening_*.log`, содержащие приватный ключ, затираются `shred`.

**Сгенерированный ключ** — скрипт предлагает показать его ещё раз прямо в терминале (мимо лога) и после явного `y` затирает `shred -uz /root/admin_ssh_key`. Если ключ не генерировался, оставшийся от прошлого прогона приватный ключ удаляется. Root по SSH к этому моменту уже запрещён, поэтому `scp` под root не сработает.

**Лишние службы.** Если включены `rpcbind`, `avahi-daemon`, `cups`, `cups-browsed`, `ModemManager`, `bluetooth` — скрипт предлагает отключить каждую (в `--yes` — только перечисленные в `DISABLE_SERVICES`); откат включает их обратно.

**Слушающие порты** — список того, что слушает не только localhost: удобно сверить с правилами UFW.

**Итог** — статус каждого шага: `[OK]`, `[!N]` (N предупреждений, подробности выше и в логе), `[--]` (выключено настройкой), `[skip]` (не выбран), с короткой пометкой (порт SSH, режим `/tmp`, форвардинг и т.д.). Ниже — путь к логу и команда отката этого прогона.

## Шифрование LUKS (режим --luks)

Шифрование встроено в скрипт как режим `--luks`. Полное руководство и восстановление — в **`LUKS.md`**.

**Что LUKS даёт на VPS.** Защищает данные «в покое»: снапшоты и бэкапы у провайдера, отключённые тома, списанные диски, изъятие выключенного сервера. **Не защищает** от гипервизора, читающего RAM работающей ВМ, и от взлома самой работающей системы — там данные уже расшифрованы.

```bash
bash ubuntu_hardening.sh --luks status
bash ubuntu_hardening.sh --luks data /dev/vdb --name pgdata --mount /var/lib/postgresql
bash ubuntu_hardening.sh --luks file /var/lib/secure.img 20G
bash ubuntu_hardening.sh --luks swap
bash ubuntu_hardening.sh --luks remote-unlock --tang http://tang.example.net
```

### Данные Docker

Если шифровать всю ОС избыточно, достаточно зашифровать данные. Для Docker это не только тома — ещё логи контейнеров и их записываемые слои.

```bash
sudo bash ubuntu_hardening.sh --luks data /dev/vdb     # или --luks file /var/lib/secure.img 50G
sudo bash ubuntu_hardening.sh --luks docker
```

- `/var/lib/docker` (и `/var/lib/containerd`, если используется) копируется на том и подключается обратно bind-монтированием — пути и конфиги Docker не меняются;
- пустые точки монтирования делаются неизменяемыми (`chattr +i`), а `docker.service` получает `RequiresMountsFor=` — без открытого тома Docker не стартует и не может писать на открытый диск (иначе, например, Postgres создал бы новую пустую базу прямо на системном диске);
- при ручной разблокировке Docker запускается командой `sudo luks-unlock securedata`, останавливается вместе с томом — `sudo luks-lock securedata`;
- скрипт перечисляет, что **останется незашифрованным**: bind-монтирования вне тома, каталоги compose-проектов (`.env`), логирование в journald;
- старый каталог сохраняется как `*.pre-luks` до явного удаления.

Бэкапы шифруйте отдельно (restic, borg, age), swap — `--luks swap`. Подробнее — `LUKS.md`.

### Шифрование всего сервера

Корень, с которого система работает, нельзя зашифровать «на лету», поэтому два режима:

| | `--luks encrypt-root <раздел>` | `--luks encrypt-root-auto` |
|---|---|---|
| Где запускать | rescue-система провайдера | на самом сервере |
| `/boot` внутри корня | создаёт раздел `/boot` 1 ГБ из конца корня | не поддерживается |
| Пароль | задаётся сразу | после загрузки: `--luks encrypt-root-finish` |
| Ubuntu 26.04 (dracut) | да | нет (только 22.04/24.04) |

Общие требования: **снапшот диска**, VNC-консоль, корень — ext4 на обычном разделе (не LVM), загрузчик GRUB, свободно ≥ 512 МБ.

```bash
# из rescue-системы:
bash ubuntu_hardening.sh --luks encrypt-root /dev/vda1

# или на работающем сервере:
sudo bash ubuntu_hardening.sh --luks encrypt-root-auto      # подготовка + reboot
sudo bash ubuntu_hardening.sh --luks encrypt-root-finish    # сразу после загрузки
```

**`encrypt-root-auto`** добавляет в initramfs временный ключ и сценарий: при следующей загрузке, до монтирования корня, раздел шифруется на месте, затем загрузка продолжается. Обрыв питания — шифрование продолжится при следующей загрузке; не началось — система грузится как раньше (журнал `/boot/luks-convert.log`). **До `encrypt-root-finish` защиты нет** — ключ лежит на незашифрованном `/boot`. Finish задаёт пароль, проверяет каждый initramfs и только потом удаляет временный ключ; предлагает сменить мастер-ключ на случай снапшотов, сделанных в промежутке.

После шифрования пароль нужен при **каждой загрузке**: VNC, SSH (`--luks remote-unlock`, dropbear) или автоматически через Tang. Подробности, ограничения и восстановление — `LUKS.md`.

**Способ разблокировки томов с данными (`--unlock`):**

| Способ | Как работает | Когда выбирать |
|---|---|---|
| `manual` (по умолчанию) | После загрузки том закрыт; после входа — `sudo luks-unlock <имя>` | Ключа на сервере нет вообще — самый сильный вариант |
| `keyfile` | Ключ в `/etc/cryptsetup-keys.d/`, автомонтирование | Root тоже зашифрован или угроза — утечка отдельного volume |
| `tang` | Clevis + Tang: автоматически, пока сервер «видит» ваш Tang | Парк серверов; Tang — у другого провайдера |

Для `manual` сервисы, работающие с этими данными, перечислите в `/etc/luks-unlock.d/<имя>.services` и уберите из автозапуска — `luks-unlock` запустит их после монтирования, `luks-lock` остановит.

**Решения, заложенные в режим:**

- LUKS2, `aes-xts-plain64`/512, argon2id, сектор 4096; если vCPU не отдаёт AES-NI — предупреждение и предложение Adiantum;
- память argon2id ограничена ¼ RAM (64 МБ – 1 ГБ): стоимость фиксируется при форматировании, и дефолт cryptsetup может не дать открыть том на 1-гигабайтном VPS или после понижения тарифа;
- `no_read/no_write_workqueue` сохраняются в заголовке — меньше задержка на virtio/NVMe;
- TRIM выключен по умолчанию: на общем хранилище он раскрывает карту занятых блоков;
- резервная копия заголовка — в `/root/luks-backup/`, её нужно скачать и удалить с сервера;
- `swap`: swap-файл заменяется на zram (swap поверх loop-устройства склонен к взаимоблокировкам), swap-раздел шифруется dm-crypt со случайным ключом при каждой загрузке, адресация по PARTUUID;
- `remote-unlock`: dropbear в initramfs с ключами администратора и принудительной командой `cryptroot-unlock`, сеть через параметр ядра `ip=` (статический IP или DHCP; только IPv4), опционально Tang; порт нужно открыть в firewall **провайдера** — UFW в initramfs не работает;
- деструктивный режим `data` отказывается работать с примонтированным, swap-, LVM- или RAID-устройством и требует ввести путь устройства вручную;
- правила auditd для `/etc/crypttab`, ключей и initramfs — в `/etc/audit/rules.d/60-luks.rules` (при immutable-правилах применятся после reboot).

## Сознательные отклонения от CIS

Эти решения оправданы спецификой VPS/VDS — это **не пробелы**, а осознанный выбор:

| Отклонение | CIS | Причина |
|---|---|---|
| `disk_full_action = ROTATE` (не halt/single) | 6.2.2.3 | halt = недоступный VPS без физической консоли |
| auditd `-f 1` (syslog), не `-f 2` (паника) | — | паника ядра при сбое аудита уронит VPS в офлайн |
| Нет аудита `socket`/`connect` | — | тысячи событий/сек, переполнение backlog; `bind` покрывает значимые случаи |
| USB/Firewire не в blacklist | 1.1.1 | на виртуалке устройств нет; риск задеть virtio-драйверы |
| `chrony` вместо `systemd-timesyncd` | 2.3 | точнее и быстрее восстанавливается на VPS |
| `ptrace_scope = 1`, не `2` | 1.5.2 | сохранить `strace`/`gdb` для диагностики без физического доступа |
| `kernel.sysrq = 0` | — | SysRq не нужен (есть консоль провайдера) и является вектором атаки |
| `Automatic-Reboot = false` | — | неконтролируемый reboot продакшн-VPS недопустим |
| Пароль GRUB не ставится | 1.4.1 | без IP-KVM усложняет восстановление через консоль провайдера |
| userns-ограничения легко отключаемы | — | не ломать rootless-контейнеры без ведома администратора |
| История root не отключается | — | отключение — антифорензика; аудит ведёт auditd |
| AppArmor: complain-профили не форсируются | 1.3.1.4 | часть профилей намеренно в complain; принудительный enforce ломает программы. Включается `APPARMOR_ENFORCE_ALL="yes"` |
| `rp_filter = 2` при нескольких интерфейсах | 3.3.7 | строгий режим ломает асимметричную маршрутизацию с приватной сетью провайдера |
| `ip_forward = 1` при Docker/Podman/LXD/WireGuard | 3.3.1 | иначе контейнеры и VPN теряют сеть после `sysctl --system` |
| `accept_ra` не меняется при глобальном IPv6 | 3.3.9 | IPv6-маршрут по умолчанию у многих провайдеров приходит через RA |
| `/tmp` на диске (bind) при RAM < 2 ГБ | 1.1.2.1 | tmpfs отнимал бы память у сервисов; флаги `nosuid,nodev,noexec` сохранены |
| `pam_faillock` выключен по умолчанию | 5.3.3.1 | при заблокированном root 5 ошибок означают 15 минут без sudo. Включается `ENABLE_FAILLOCK=yes` |
| AIDE выключен по умолчанию | 6.1 | долгая инициализация и шум после каждого обновления. Включается `ENABLE_AIDE=yes` |
| Порт SSH 22 допустим | — | смена порта не защищает, а лишь уменьшает шум в логах |

## Подключение после настройки

```bash
# Ключи root или свой ключ — тот же ключ, что и раньше
ssh -p <PORT> <user>@<IP>

# Сгенерированный на сервере ключ (пароль ключа при каждом входе)
ssh -p <PORT> -i ./admin_ssh_key <user>@<IP>

# Через ssh-agent (пароль ключа один раз за сессию)
eval $(ssh-agent)
ssh-add ./admin_ssh_key
ssh -p <PORT> <user>@<IP>
```

`~/.ssh/config` на клиентской машине:

```sshconfig
Host myserver
    HostName      <IP>
    Port          <PORT>
    User          <user>
    IdentityFile  ~/.ssh/admin_ssh_key
    AddKeysToAgent yes
```

`<user>` — имя администратора, выбранное при запуске (по умолчанию `admin`).

После этого достаточно: `ssh myserver`

## Диагностика и мониторинг

```bash
# Сводная проверка всего, что настраивает скрипт
sudo bash ubuntu_hardening.sh --audit

aa-status
```

## Что требует перезагрузки

- **Blacklist модулей ядра** — если модуль был загружен и не выгрузился
- **`/tmp` при смене типа** (tmpfs ↔ диск), **`/var/tmp` и `/home`** — если не применились в текущей сессии
- **Неизменяемые правила auditd** (`-e 2`) — любые изменения правил, включая `60-luks.rules` и `70-privileged.rules`
- **`kexec_load_disabled`** и ограничения user namespaces — на части ядер
- **`hidepid`** и **параметры ядра в GRUB** (`KERNEL_CMDLINE_HARDENING`)
- **SSH-разблокировка root** (`--luks remote-unlock`) — первую перезагрузку проверяйте с открытой VNC-консолью
- **`--luks encrypt-root-auto`** — шифрование корня происходит при перезагрузке; сразу после неё — `--luks encrypt-root-finish`

```bash
reboot
# затем:
ssh -p <PORT> <user>@<IP>
sudo bash ubuntu_hardening.sh --audit
```

## Восстановление при потере доступа

Сначала — консоль провайдера (VNC/KVM). Root заблокирован паролем, поэтому для входа в консоль используйте администратора или режим recovery/rescue-систему провайдера.

```bash
# Откатить все файлы последнего прогона (sshd, UFW, PAM, sysctl, fstab, ...)
bash ubuntu_hardening.sh --rollback                  # список прогонов
bash ubuntu_hardening.sh --rollback <метка>

# Точечно: исходные файлы лежат с полными путями
ls /var/backups/ubuntu_hardening/<метка>/files/etc/
cp -a /var/backups/ubuntu_hardening/<метка>/files/etc/ssh/sshd_config /etc/ssh/ && systemctl restart ssh
#   drop-in sshd с Port/ListenAddress, убранные скриптом, — там же, в moved/

# Разблокировать root (вход через консоль провайдера)
passwd root

# UFW: экстренно выключить; Fail2ban: снять бан со своего IP
ufw disable
fail2ban-client set sshd unbanip <ваш_IP>

# faillock: снять блокировку sudo
faillock --user <user> --reset

# LUKS: резервные копии crypttab/fstab и заголовков
ls /root/luks-backup/
cryptsetup open /dev/vdb securedata && mount /dev/mapper/securedata /srv/secure

# Разбор причин
less /root/hardening_harden_*.log
```

Если система не грузится из-за записи в fstab — в режиме recovery восстановите `/etc/fstab` из каталога резервных копий. Если SSH не поднимается — `journalctl -xe -u ssh` и проверьте, не включился ли обратно `ssh.socket`.

Прогоны v3 и старше хранили копии рядом с файлами (`*.bak.<timestamp>`, `/root/sshd_config.d.bak`) — они остаются на месте.

## Повторный запуск скрипта

Скрипт рассчитан на повторные запуски:

- **ответы прошлого прогона — умолчания**: администратор, порт, порты UFW, NTP и все настройки из `/etc/ubuntu_hardening.conf` предлагаются как ответ по `Enter`; порты UFW больше не теряются после `ufw --force reset`;
- **root заблокирован** — запускайте через `sudo -i` из-под администратора;
- **пароль администратора** спрашивается только если вы хотите его сменить;
- **auditd при immutable**: файлы правил записываются, загрузка откладывается до перезагрузки;
- дубликаты не появляются: ключ добавляется, только если его нет; строки `127.0.1.1`, записи fstab (по точке монтирования), `pam_wheel`, `login.defs`, drop-in файлы заменяются, а не дописываются;
- **переход с v3**: `chrony.conf` и `pwquality.conf`, перезаписанные v3, возвращаются к файлам пакета (настройки переезжают в drop-in); дубли в `limits.conf` убираются; `chattr +i` с `resolv.conf` снимается; права `sudo.log` исправляются; `-b` auditd начинает действовать;
- **переход с v2**: `remount-home.service` удаляется, `/var/tmp` переводится на собственный bind, логи с приватным ключом затираются, `50unattended-upgrades` переопределяется `52-…`;
- каждый прогон создаёт свою точку отката.

## Ручное включение форвардинга

Docker, Podman, LXD и WireGuard определяются автоматически (`IP_FORWARD=auto`). Для своего VPN-сервера или маршрутизатора:

```bash
# при запуске
UH_IP_FORWARD=yes UH_TCP_FORWARDING=yes bash ubuntu_hardening.sh --only ssh,sysctl
#   (шаги ssh и sysctl; GATEWAY_PORTS=yes — только если нужен проброс портов наружу)

# разрешить маршрутизируемый трафик в UFW (по умолчанию deny routed)
ufw route allow in on wg0 out on eth0
```

После ручной правки `sshd_config`: `sshd -t && systemctl restart ssh`. Ручные правки файлов скрипта перезапишутся при следующем прогоне соответствующего шага — задавайте значения через `--config`.
