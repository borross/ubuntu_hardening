# Ubuntu Hardening Script — VPS/VDS Edition (v3.1)

Скрипт автоматизированного харденинга Ubuntu 22.04 / 24.04 / 26.04 для виртуальных серверов.
Запускается от `root` сразу после получения чистого VPS/VDS и проводит полную настройку безопасности в один проход. Отдельный режим `--luks` добавляет шифрование LUKS2 — от отдельных дисков до всего сервера.

Основан на практиках **CIS Ubuntu Linux Benchmark** с поправками на специфику VPS: физического доступа нет, консоль — только через панель провайдера, поэтому все меры, способные «уронить» сервер в офлайн (паника ядра при сбое аудита, пароль GRUB, агрессивный blacklist драйверов), либо смягчены, либо сознательно исключены. Каждое такое решение задокументировано в разделе [Сознательные отклонения от CIS](#сознательные-отклонения-от-cis).

## Что нового в v3

**Исправленные ошибки v2**

| Исправление | Суть |
|---|---|
| **Приватный ключ в логе** | v2 печатала ключ через `cat`, а весь вывод шёл через `tee` в `/root/hardening_*.log` — ключ оставался в логе навсегда, `shred` в шаге 20 его не касался. Теперь ключ выводится напрямую в `/dev/tty` и в лог не попадает; старые логи с ключом затираются в шаге 20 |
| **Инструкция шага 20** | v2 советовала `scp -P 22 root@…`, но к этому моменту root по SSH запрещён и порт сменён. Теперь ключ можно показать ещё раз на экране |
| **`su` не ограничивался** | В Ubuntu строка выглядит как `# auth required pam_wheel.so` (пробел после `#`). Проверка `^#auth` её не находила, а поиск `pam_wheel.so` срабатывал на комментарий — в итоге не менялось ничего. Теперь строка раскомментируется с `group=sudo` |
| **Политика паролей запаздывала** | `pwquality.conf` записывался в секции 16, уже после `passwd` в секции 3. Теперь — до задания пароля, с `enforce_for_root` (без него pwquality для root только предупреждает) |
| **Риск потери доступа через sudoers** | Root блокируется в секции 5, а sudoers правился в секции 15 с одним лишь предупреждением при ошибке. Теперь файл проверяется `visudo -c -f` до установки |
| **`remount-home.service` падал** | `mount -o remount /home` не работает, если `/home` не точка монтирования (типично для VPS). Заменено на bind-монтирование в fstab; старый unit удаляется |
| **Отключался постквантовый SSH** | `KexAlgorithms` v2 убирал `sntrup761x25519` / `mlkem768x25519`, включённые в OpenSSH по умолчанию. Теперь список строится из `ssh -Q kex` с гибридами первыми |
| **`sshd_config` без проверки** | Конфиг писался сразу на место; при ошибке битый файл оставался. Теперь — временный файл, `sshd -t -f`, установка, проверка `sshd -T` |
| **`/var/tmp` терялся при reboot** | Был привязан к tmpfs `/tmp`. Теперь — bind на себя с `noexec`, содержимое постоянно |

**Улучшения**

| Изменение | Суть |
|---|---|
| **Режим `--luks`** | Шифрование LUKS2: отдельный диск, файл-контейнер, swap, SSH-разблокировка root через dropbear. См. [раздел](#шифрование-luks-режим---luks) и `LUKS.md` |
| **Шифрование всего сервера (v3.1)** | `--luks encrypt-root` из rescue-системы (сам создаёт `/boot`, если его нет) и `--luks encrypt-root-auto` с работающей системы — шифрование при следующей загрузке. См. [раздел](#шифрование-всего-сервера) |
| **Данные Docker (v3.1)** | `--luks docker`: тома, логи и слои контейнеров (включая containerd) переносятся на зашифрованный том; Docker не стартует без тома. См. [раздел](#данные-docker) |
| **Ubuntu 26.04 / dracut (v3.1)** | Генератор initramfs определяется автоматически; на dracut сетевая разблокировка — через Tang (`clevis-dracut`), dropbear там не работает |
| **Свой публичный ключ** | Третий вариант в выборе ключа — приватная часть вообще не появляется на сервере |
| **Имя администратора** | Спрашивается при запуске; `admin` — одно из первых имён в словарях перебора |
| **AppArmor без массового enforce** | v2 переводила в enforce все профили, ломая намеренно оставленные в complain. Теперь — отчёт; прежнее поведение: `APPARMOR_ENFORCE_ALL="yes"` |
| **auditd** | Время, mount, hostname/сеть, PAM, AppArmor, входы и сессии, systemd-юниты, `ld.so.preload`, неудачный доступ к файлам, kexec; b32 для модулей и `bind`; `/usr/bin/kmod` вместо симлинков `/sbin/*` |
| **sysctl** | `rp_filter` по числу интерфейсов; `kexec_load_disabled`, `unprivileged_bpf_disabled`, `bpf_jit_harden`, `ldisc_autoload`, `unprivileged_userfaultfd`, `accept_source_route`; убран `tcp_syn_retries` |
| **Автообновления** | Свой файл `52-…` с `#clear` вместо перезаписи `50unattended-upgrades`; nginx/apache больше не исключены; needrestart |
| **UFW** | UDP-порты и диапазоны (`443/udp`, `8000:8100/tcp`); если UFW уже активен — новый порт SSH открывается до перезапуска sshd |
| **Fail2ban** | `ignoreip`, режим `aggressive`, jail `recidive` |
| **chrony** | Сохранены `rtcsync`, `leapsectz`, `confdir`/`sourcedir` (NTP провайдера по DHCP), `ntsdumpdir` |
| **Прочее** | `/tmp` с ограничением `size=`; `/etc/shadow` `640 root:shadow`; sudo `use_pty` и совместимость с sudo-rs (26.04); motd-news и apt-news отключены; `/etc/ubuntu_hardening.conf` с параметрами прогона |

## Что нового в v2

| Исправление | Суть |
|---|---|
| **ssh.socket** | Ubuntu 22.10+ запускает SSH через socket-активацию, при которой `Port` из `sshd_config` игнорируется. Скрипт отключает `ssh.socket` — это истинная причина проблемы «порт не поменялся» |
| **Контрольная точка входа** | Проверка SSH-входа под `admin` теперь **до** блокировки root, а не в конце скрипта |
| **Auditd: причина backlog exceeded** | Удалены правила аудита `socket`/`connect` — они генерировали тысячи событий/сек. Увеличение backlog лечило симптом, а не причину |
| **Auditd 3.x** | Убраны `dispatcher = /sbin/audispd` и `disp_qos` — удалены из auditd 3.x (Ubuntu 22.04+), с ними демон мог не стартовать |
| **Auditd: arch=b32** | Ключевые правила продублированы для 32-битных syscalls — без этого аудит обходился 32-битными вызовами |
| **/etc/ssh 755** | Было `chmod 700 /etc/ssh` — это ломало исходящие `ssh`/`scp`/`git` для непривилегированных пользователей (нет доступа к `ssh_config`) |
| **logrotate для audit удалён** | auditd ротирует логи сам (`max_log_file_action=ROTATE`); параллельный logrotate давал двойную ротацию и разрывы аудита |
| **Тип ключа на выбор** | ed25519 (рекомендуется) или ecdsa-521 |
| **passwd в цикле** | 3 ошибки ввода пароля больше не роняют скрипт из-за `set -e` |
| **chrony minsources** | При одном пользовательском NTP-сервере ставится `minsources 1` — иначе время никогда не считалось бы синхронизированным |
| **UFW: опрос портов** | Перед `ufw reset` показываются слушающие порты и можно открыть дополнительные (80, 443 и т.д.) |
| **noexec /tmp и apt** | Временный каталог apt перенесён в `/var/lib/apt/tmp` — иначе ночные unattended-upgrades могли падать |
| **userns под ядро** | `kernel.unprivileged_userns_clone` пишется только если существует в ядре; на 24.04+/26.04 используется `apparmor_restrict_unprivileged_userns` |
| **Повторный запуск** | При immutable-правилах auditd (`-e 2`) секция 13 пропускается с предупреждением вместо аварийного завершения |
| **usermod при повторном запуске** | Существующий пользователь теперь гарантированно добавляется в sudo |
| **rsyslog в зависимостях** | Минимальные образы 24.04+ могут идти без rsyslog, на котором построено логирование sudo |
| **Лог выполнения + trap** | Весь вывод дублируется в `/root/hardening_<дата>.log`; при ошибке trap показывает номер строки |
| **Drop-in c Port** | Конфликтующие файлы `/etc/ssh/sshd_config.d/*` с директивой `Port` перемещаются в `/root/sshd_config.d.bak` |
| **История root** | Симлинк `.bash_history → /dev/null` убран — это антифорензика; аудит команд ведёт auditd (`priv_exec`) |
| **Мелочи** | `dpkg -s` вместо `dpkg -l`; фикс приоритета операторов в bind-mount `/var/tmp`; валидация NTP-серверов; `AddressFamily` в переменной |

## Требования

| Параметр | Значение |
|---|---|
| ОС | Ubuntu 22.04 / 24.04 / 26.04 LTS |
| Платформа | VPS / VDS (KVM, XEN, VMware, Hyper-V) |
| Пользователь | `root` |
| Сеть | Доступ в интернет для установки пакетов |
| Доступ | VNC или консоль провайдера на случай потери SSH |

Версия ОС проверяется при старте по `/etc/os-release`: для 22.04 / 24.04 / 26.04 скрипт продолжает без вопросов, для любой другой — предупреждает и запрашивает подтверждение.

> ⚠️ **Перед запуском убедитесь, что у вас открыта консоль провайдера (VNC/KVM).** Если SSH-сессия оборвётся в процессе, вы сможете продолжить через неё. Особенно это важно на этапах смены порта SSH и блокировки root.

## Быстрый старт

```bash
# Скачать скрипт на сервер
wget -O ubuntu_hardening.sh https://raw.githubusercontent.com/borross/ubuntu_hardening/refs/heads/main/ubuntu_hardening.sh

# Проверить содержимое перед запуском
less ubuntu_hardening.sh

# Запустить
bash ubuntu_hardening.sh
```

Скрипт интерактивный — задаёт вопросы по имени администратора, порту SSH, ключу, имени хоста, FQDN, DNS, часовому поясу, NTP, дополнительным портам UFW и шифрованию. Всё, что можно пропустить, пропускается нажатием `Enter`. Запуск через пайп (`curl … | bash`) отклоняется: скрипту нужен терминал.

Весь вывод дублируется в лог `/root/hardening_harden_<дата>_<время>.log` (права `600`) — при разборе проблем это первое, куда стоит смотреть. Приватный ключ и пароли в лог не попадают. При аварийной остановке trap печатает номер строки, на которой произошёл сбой.

## Аргументы командной строки

```bash
bash ubuntu_hardening.sh                      # полный харденинг (интерактивно)
bash ubuntu_hardening.sh --luks <режим> ...   # только шифрование LUKS2
bash ubuntu_hardening.sh --help               # справка
```

| Режим `--luks` | Что делает |
|---|---|
| `status` | Состояние шифрования: root, тома, swap, crypttab, AES-NI |
| `data <устройство>` | Зашифровать отдельный диск/раздел (**данные удаляются**) |
| `file <путь> <размер>` | Файл-контейнер, например `/var/lib/secure.img 20G` |
| `swap` | Убрать открытый swap: файл → zram, раздел → dm-crypt со случайным ключом |
| `remote-unlock` | Ввод пароля root-LUKS по сети: dropbear в initramfs (22.04/24.04) или Tang (26.04) |
| `docker` | Перенести данные Docker/containerd на зашифрованный том (создайте его заранее: `data` или `file`) |
| `encrypt-root <раздел>` | Зашифровать корень из rescue-системы; если `/boot` внутри корня — создать раздел `/boot` |
| `encrypt-root-auto` | Зашифровать корень с работающей системы при следующей загрузке (нужен отдельный `/boot`, 22.04/24.04) |
| `encrypt-root-finish` | После такой загрузки: задать пароль, удалить временный ключ |
| `encrypt-root-cancel` | Отменить подготовку `encrypt-root-auto` |

| Опция | По умолчанию | Назначение |
|---|---|---|
| `--name <имя>` | `securedata` | имя маппинга `/dev/mapper/<имя>` |
| `--mount <путь>` | `/srv/secure` | точка монтирования |
| `--fs ext4\|xfs` | `ext4` | файловая система |
| `--mount-opts <опции>` | `defaults,nodev,nosuid` | опции монтирования |
| `--unlock manual\|keyfile\|tang` | `manual` | способ разблокировки при загрузке |
| `--tang <URL>` | — | Tang-сервер (для `--unlock tang` и root) |
| `--discards` | выкл. | TRIM (раскрывает занятые блоки) |
| `--no-perf` | — | не использовать `no_read/no_write_workqueue` |
| `--prefill` | выкл. | заполнить том через dm-crypt |
| `--cipher`, `--key-size` | `aes-xts-plain64`, `512` | шифр |
| `--user <имя>` | из `/etc/ubuntu_hardening.conf` | чьи ключи пускать в initramfs |
| `--dropbear-port <n>` | `2222` | порт SSH в initramfs |
| `--prepare` | — | `remote-unlock` до шифрования root |

Подробности — в разделе [Шифрование LUKS](#шифрование-luks-режим---luks) и в `LUKS.md`.

## Переменные конфигурации

Настраиваются в начале файла скрипта:

```bash
ADMIN_USER="admin"               # имя по умолчанию (будет переспрошено интерактивно)
SSH_PORT="20202"                 # порт по умолчанию (будет переспрошен интерактивно)
KEY_PATH="/root/admin_ssh_key"   # путь для сохранения ключевой пары

# Семейство адресов для SSH:
#   any  — IPv4 + IPv6 (безопасное значение по умолчанию)
#   inet — только IPv4 (НЕ ставьте на IPv6-only VPS — потеряете доступ!)
SSH_ADDRESS_FAMILY="any"

# Форвардинг — отключён по умолчанию, включайте осознанно
TCP_FORWARDING="no"
GATEWAY_PORTS="no"
X11_FORWARDING="no"

# yes — перевести ВСЕ complain-профили AppArmor в enforce (может ломать программы)
APPARMOR_ENFORCE_ALL="no"

# Параметры прогона для режима --luks и повторных запусков
STATE_FILE="/etc/ubuntu_hardening.conf"
```

Ниже в том же блоке — значения по умолчанию для LUKS (`LUKS_NAME`, `LUKS_MOUNT`, `LUKS_UNLOCK` и др.); удобнее задавать их опциями `--luks`.

## Интерактивные вопросы и контрольные точки

Порядок диалогов при выполнении:

| Этап | Вопрос | По умолчанию |
|---|---|---|
| Предстарт | Имя администратора | `admin` |
| Предстарт | Порт SSH (1024–65535) | `20202` |
| Предстарт | Ключ: сгенерировать ed25519 / ecdsa-521 или **вставить свой публичный** | ed25519 |
| Секция 1 | Имя хоста, FQDN, DNS (2 адреса), часовой пояс, NTP-серверы | текущие значения / пулы Ubuntu |
| Секция 2 | Пароль приватного ключа (только при генерации) | — обязателен |
| Секция 2 | Пауза «сохраните приватный ключ» (только при генерации) | — |
| Секция 3 | Пароль администратора (для sudo, политика 16+ символов) | — обязателен, в цикле |
| Секция 4 | **Контрольная точка**: «вход под администратором работает?» `y/n` | `n` прерывает скрипт **до** блокировки root |
| Секция 6 | Дополнительные порты UFW (TCP, `/udp`, диапазоны) | только SSH |
| Секция 19.5 | Шифрование LUKS: диск / файл / swap / SSH-разблокировка root | пропустить |
| Секция 20 | «Показать ключ ещё раз?», «Удалить приватный ключ с сервера?» | `N` / `N` |

Контрольная точка в секции 4 — главный предохранитель: root блокируется только после того, как вы из **нового терминала** подтвердили, что ключевой вход под администратором на новом порту работает.

## Что делает скрипт

Нумерация секций соответствует выводу скрипта.

### 0. Предстартовые проверки и обновление системы

**Проверки:** запуск от root, наличие терминала, версия Ubuntu, наличие `/etc/os-release`.

**Расчёт лимитов логирования** — две независимые метрики, посчитанные до начала изменений:

```
Квота логов  = свободное место на разделе /var/log ÷ 10   (10%, зажато 50–2048 МБ)
               делится на 5 файлов ротации auditd
Audit backlog = RAM_МБ × 8                                 (зажато 8192–65536)
```

| RAM VPS | Backlog |
|---|---|
| 512 МБ – 1 ГБ | 8192 (минимум) |
| 2 ГБ | 16384 |
| 4 ГБ | 32768 |
| 8 ГБ+ | 65536 (максимум) |

Backlog — буфер в **оперативной памяти** ядра, поэтому считается от RAM, а не от диска. Расчёт выводится на экран при старте.

**Обновление и пакеты:** `apt-get upgrade` в неинтерактивном режиме (`--force-confdef`/`--force-confold` — не задавать вопросов о конфигах) и установка:

```
ufw  fail2ban  auditd  audispd-plugins  libpam-pwquality
unattended-upgrades  apt-listchanges  acl  curl  wget  gnupg2  chrony  rsyslog  needrestart
```

`rsyslog` указан явно: минимальные cloud-образы Ubuntu 24.04+ могут поставляться без него, а на нём построено логирование sudo (секция 15). Гипервизор определяется через `systemd-detect-virt`.

### 1. Имя хоста, FQDN, DNS, часовой пояс, NTP

Единственный полностью интерактивный раздел; каждый пункт пропускается через `Enter`.

**Имя хоста** — `hostnamectl set-hostname`, валидация по RFC 1123 (только `a-z`, `0-9`, дефис, ≤63 символов). `/etc/hosts` обновляется автоматически — без этого `sudo` выдаёт раздражающее `unable to resolve host`.

**FQDN** — валидация по RFC 1123 (метки через точки, TLD ≥2 символов), запись в `/etc/hosts`:

```
127.0.1.1    server01.example.com  server01
```

Благодаря такой записи `hostname --fqdn` и `hostname -s` работают корректно без реального DNS.

**DNS** — основной и резервный IPv4-адрес, каждый валидируется (формат + октеты 0–255):

| Провайдер | Основной | Резервный |
|---|---|---|
| Cloudflare | `1.1.1.1` | `1.0.0.1` |
| Google | `8.8.8.8` | `8.8.4.4` |
| Quad9 | `9.9.9.9` | `149.112.112.112` |
| Yandex | `77.88.8.8` | `77.88.8.1` |

Если активен `systemd-resolved` — настройка через drop-in `/etc/systemd/resolved.conf.d/custom-dns.conf` с DNS-over-TLS (`opportunistic`) и DNSSEC (`allow-downgrade`). Иначе — прямая запись в `/etc/resolv.conf` с защитой от перезаписи DHCP-клиентом (`chattr +i`).

**Часовой пояс** — `timedatectl set-timezone`, значение проверяется по `timedatectl list-timezones` перед применением.

**NTP через chrony.** Chrony предпочтительнее `systemd-timesyncd` на VPS:

| | systemd-timesyncd | chrony |
|---|---|---|
| Точность | средняя | высокая |
| После долгого простоя VPS | медленно догоняет | быстрый `makestep` |
| Нестабильная сеть | хуже | `maxdistance` отсекает плохие источники |
| Логирование | минимальное | measurements/statistics/tracking |

По умолчанию — пулы `0-3.ubuntu.pool.ntp.org` + `time.cloudflare.com` с NTS (аутентифицированный NTP). Пользовательские серверы валидируются (IPv4 или hostname по RFC 1123); невалидные пропускаются, при нуле валидных — откат на серверы по умолчанию. `minsources` подстраивается автоматически: `1` при единственном сервере, иначе `2`. `chronyc` слушает только localhost. Сохранены стандартные директивы Ubuntu: `rtcsync` (синхронизация аппаратных часов), `leapsectz right/UTC`, `confdir`/`sourcedir` — в том числе `/run/chrony-dhcp`, куда попадают NTP-серверы провайдера, выданные по DHCP; `ntsdumpdir` кэширует NTS-cookie. Прежний `chrony.conf` сохраняется как `.bak.<timestamp>`. После запуска — принудительный `chronyc makestep` и вывод статуса синхронизации.

`systemd-timesyncd` отключается, чтобы не конфликтовать с chrony.

### 2. SSH-ключ администратора

Три варианта на выбор:

| Вариант | Где появляется приватный ключ |
|---|---|
| **Свой публичный ключ** (рекомендуется) | Только у вас. Строка проверяется `ssh-keygen -l`; RSA короче 3072 бит отклоняется |
| Сгенерировать ed25519 | На сервере, затем скачать и удалить в секции 20 |
| Сгенерировать ecdsa-521 | То же — для сред, где NIST P-521 требуется явно |

```bash
# у себя — для варианта «свой ключ»
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/admin_ssh_key
cat ~/.ssh/admin_ssh_key.pub        # эту строку вставить в диалог

# на сервере — при генерации (-a 100: стойкое шифрование ключа паролем)
ssh-keygen -t ed25519 -a 100 -f /root/admin_ssh_key -C "<user>@<host>-<дата>"
```

При генерации ключ создаётся **с паролем**.

| Файл | Права | Назначение |
|---|---|---|
| `/root/admin_ssh_key` | `600` | приватный ключ (только при генерации) — скачать и удалить в секции 20 |
| `/root/admin_ssh_key.pub` | `644` | публичный ключ — остаётся на сервере |

**Приватный ключ выводится напрямую в терминал (`/dev/tty`), мимо лога выполнения.** В v2 он попадал в `/root/hardening_*.log` и оставался там после удаления самого ключа. Пока root ещё может входить по SSH, ключ можно скачать:

```bash
# из второго терминала, ДО секции 4:
scp root@<IP>:/root/admin_ssh_key ./admin_ssh_key
```

### 3. Создание пользователя-администратора

Имя спрашивается при запуске (по умолчанию `admin`, допустимы строчные латинские буквы, цифры, `_` и `-`). Лучше выбрать неочевидное: `admin` перебирают первым, а в sudoers Ubuntu до сих пор есть строка `%admin ALL=(ALL) ALL`.

```bash
useradd -m -s /bin/bash <user>      # с -g <user>, если такая группа уже существует
usermod -aG sudo <user>             # выполняется ВСЕГДА, и при повторном запуске
```

Особенности:

- **политика паролей записывается до `passwd`** (в v2 — после, и на пароль администратора не влияла), с `enforce_for_root`: `passwd` запускается от root, а для root pwquality без этой опции только предупреждает и принимает слабый пароль. Параметры — в [секции 16](#16-политика-паролей);
- если группа с именем пользователя уже существует, она используется как primary group через `-g`;
- `usermod -aG sudo` вынесен из ветки создания: если пользователь существовал, но не был в sudo, раньше он туда не попадал;
- `passwd` выполняется в цикле `until` — ошибки ввода не прерывают скрипт (пароль нужен только для sudo, не для SSH);
- публичный ключ добавляется в `~/.ssh/authorized_keys`, дубликаты убираются через `sort -u`; **ключ прошлого прогона удаляется** (он записан в `/etc/ubuntu_hardening.conf`), ключи, добавленные вручную, не трогаются; права `700`/`600`, владелец — реальная primary group пользователя;
- параметры прогона (администратор, порт, тело публичного ключа) сохраняются в `/etc/ubuntu_hardening.conf` (`600`) — их использует режим `--luks`.

### 4. Настройка SSH

Файл: `/etc/ssh/sshd_config`. Перед изменением — резервная копия `sshd_config.bak.<timestamp>`. Новый конфиг сначала пишется во временный файл и проверяется `sshd -t -f`; на место он попадает, только если проверка прошла.

**Права на каталог и файлы** (CIS 5.1.1–5.1.2):

```
/etc/ssh                    755   (700 ломало ssh-КЛИЕНТ для обычных пользователей —
                                   им нужен доступ к /etc/ssh/ssh_config)
/etc/ssh/sshd_config        600
ssh_host_*_key              600
ssh_host_*_key.pub          644
```

**Ключевые параметры:**

| Параметр | Значение | CIS | Обоснование |
|---|---|---|---|
| `Port` | выбранный | — | Нестандартный порт снижает шум автосканеров |
| `AddressFamily` | `any` | — | Переменная `SSH_ADDRESS_FAMILY`; `inet` опасен на IPv6-only VPS |
| `PermitRootLogin` | `no` | 5.1.20 | Прямой вход root запрещён |
| `PasswordAuthentication` | `no` | — | Только ключевая аутентификация |
| `AuthenticationMethods` | `publickey` | — | Явное требование ключа |
| `PermitEmptyPasswords` | `no` | 5.1.19 | |
| `LoginGraceTime` | `30` | 5.1.13 | `0` означало бы «без лимита» — баг оригинальной конфигурации |
| `MaxAuthTries` | `3` | 5.1.16 | Максимум попыток на соединение |
| `MaxSessions` | `5` | 5.1.17 | |
| `MaxStartups` | `5:30:20` | 5.1.18 | Защита от медленных атак на handshake |
| `ClientAliveInterval` / `CountMax` | `300` / `2` | 5.1.7 | Разрыв при 10 мин простоя |
| `AllowUsers` | `<user>` | 5.1.4 | Только указанный пользователь |
| `AllowTcpForwarding` | `no` | 5.1.5 | Туннели обходят firewall; переменная в начале скрипта |
| `GatewayPorts` / `X11Forwarding` | `no` | 5.1.22 | |
| `LogLevel` | `VERBOSE` | 5.1.14 | Fingerprint ключа в каждой записи лога |
| `Banner` | `/etc/ssh/my_banner` | 5.1.3 | Юридическое предупреждение |
| `DebianBanner` / `VersionAddendum` | `no` / `none` | — | Скрыть версию ОС от сканеров |

Устаревшие `Protocol 2` и `ChallengeResponseAuthentication` убраны: в OpenSSH 9.x они игнорируются или являются синонимами.

**Криптография** (CIS 5.1.6 / 5.1.12 / 5.1.15) — только современные алгоритмы:

```
HostKeyAlgorithms : ssh-ed25519, ecdsa-sha2-nistp521, rsa-sha2-512/256
KexAlgorithms     : mlkem768x25519-sha256, sntrup761x25519-sha512(@openssh.com),
                    curve25519-sha256, ecdh-sha2-nistp521
                    — только те, что поддерживает установленный OpenSSH (ssh -Q kex)
Ciphers           : chacha20-poly1305, aes256-gcm, aes128-gcm
MACs              : hmac-sha2-512-etm, hmac-sha2-256-etm
```

**Постквантовый обмен ключами.** Гибриды `sntrup761x25519` (OpenSSH 9.0+, Ubuntu 24.04) и `mlkem768x25519` (OpenSSH 9.9+, Ubuntu 26.04) включены в OpenSSH по умолчанию и защищают записанный сегодня трафик от расшифровки в будущем. v2 их отключала, оставляя только `curve25519`; v3 ставит их первыми, если версия OpenSSH их знает.

**Drop-in файлы.** В конце `sshd_config` стоит `Include /etc/ssh/sshd_config.d/*.conf`. sshd использует первое встреченное значение директивы, поэтому наши настройки выше Include не перебиваются drop-in файлами (например, `50-cloud-init.conf` с `PasswordAuthentication yes`), а drop-in могут добавлять только то, что мы не задали.

**Порядок применения — важен, здесь были главные баги прошлых версий:**

1. **Drop-in файлы**: `Port` и `ListenAddress`, в отличие от остальных директив, **накапливаются** — drop-in с ними открыл бы второй порт. Такие файлы перемещаются в `/root/sshd_config.d.bak`;
2. `sshd -t -f <временный файл>` — валидация до установки; затем `sshd -T` проверяет итоговую конфигурацию: порт ровно один, `PasswordAuthentication no` (иначе скрипт останавливается);
3. **UFW уже активен** (бывает в образах провайдеров) — новый порт открывается `ufw limit` **до** перезапуска sshd, иначе контрольная точка не прошла бы;
4. **Отключение `ssh.socket`**: Ubuntu 22.10+ по умолчанию запускает SSH через socket-активацию systemd, при которой порт задаёт сокет, а `Port` из `sshd_config` **игнорируется**. Это и было истинной причиной проблемы «порт не поменялся». Скрипт переключает на классический `ssh.service`;
5. Имя службы (`ssh`/`sshd`) определяется по реально запущенным юнитам;
6. Рестарт и подтверждение порта через `ss -tlnp`;
7. **Контрольная точка**: скрипт останавливается и требует подтвердить вход под администратором из нового терминала. Ответ `n` прерывает выполнение — root остаётся разблокированным, можно чинить и перезапускать.

### 5. Блокировка root

```bash
passwd -l root
```

Дополнительно `su` ограничивается членами группы `sudo` через `pam_wheel.so group=sudo` в `/etc/pam.d/su` (CIS 5.2.7) — непривилегированный пользователь не сможет даже пытаться подобрать пароль root через `su`.

> **Исправлено в v3.** В Ubuntu строка в `/etc/pam.d/su` закомментирована как `# auth       required   pam_wheel.so` — с пробелом после `#`. Проверка v2 (`^#auth`) её не находила, а поиск подстроки `pam_wheel.so` срабатывал на сам комментарий, поэтому файл не менялся. Теперь строка раскомментируется с `group=sudo` (без этой опции pam_wheel проверял бы группу root); если строки нет — вставляется перед `@include common-auth`. Перед изменением — резервная копия, после — проверка результата.

### 6. Брандмауэр UFW

**Перед сбросом правил** скрипт показывает слушающие TCP- и UDP-порты (`ss -tlnp`, `ss -ulnp`) и предлагает перечислить дополнительные — раньше `ufw --force reset` молча закрывал порты уже работающих сервисов (веб-сервер и т.п.).

Формат ввода: `80 443` (TCP), `443/udp 51820/udp` (HTTP/3, WireGuard), `8000:8100/tcp` (диапазон). Некорректные значения пропускаются; правило, отклонённое UFW, не прерывает скрипт.

```bash
ufw default deny incoming      # CIS 4.2.7
ufw default allow outgoing
ufw default deny forward
ufw limit <PORT>/tcp           # rate-limit iptables: 6 попыток за 30 сек → блок
ufw allow <port>[/tcp|udp]     # порты, указанные пользователем (с валидацией)
```

`ufw limit` вместо `ufw allow` для SSH — встроенная защита от брутфорса, работающая ещё до Fail2ban.

> 💡 **VPS-специфика:** Hetzner / DigitalOcean / Vultr предоставляют собственный firewall в панели — продублируйте правила и там. Это защита в глубину: UFW внутри гостя, firewall провайдера снаружи.

### 7. Fail2ban

Файл: `/etc/fail2ban/jail.local`

| Параметр | Значение | Комментарий |
|---|---|---|
| `backend` | `systemd` | чтение journald напрямую, не зависит от файлов логов |
| `banaction` | `ufw` | баны через тот же firewall |
| `port` | выбранный SSH-порт | подставляется автоматически |
| `maxretry` / `bantime` (sshd) | `3` / `24h` | |
| `findtime` | `10m` | окно подсчёта попыток |
| `mode` (sshd) | `aggressive` | ловит перебор ключами и обрывы до аутентификации (сканеры) |
| `ignoreip` | `127.0.0.1/8 ::1` | добавьте сюда IP своего офиса/VPN |
| jail `recidive` | 3 бана за сутки → бан на неделю | повторные нарушители |

### 8. Защита cron

```bash
chown root:root /etc/crontab /etc/cron.{hourly,daily,weekly,monthly,d}/
chmod og-rwx    /etc/crontab /etc/cron.{hourly,daily,weekly,monthly,d}/
```

Создаются `/etc/cron.allow` и `/etc/at.allow` (600), содержащие только `root`; файлы `cron.deny` / `at.deny` удаляются (CIS 2.4.1). При наличии обоих файлов `allow` имеет приоритет, но явное удаление `deny` исключает неоднозначность. Обработка `at` — только если он установлен.

### 9. Защита разделов

Файл: `/etc/fstab` (резервная копия перед изменением). CIS 1.1.2.x.

| Раздел | Флаги | От чего защищает |
|---|---|---|
| `/tmp` | tmpfs `nosuid,nodev,noexec,relatime,mode=1777,size=<¼ RAM>` | Выполнение залитых скриптов/бинарников из /tmp |
| `/dev/shm` | `nosuid,nodev,noexec` | Исполнение из разделяемой памяти |
| `/var/tmp` | bind на себя `nosuid,nodev,noexec` | То же, содержимое переживает reboot |
| `/home` | `nosuid,nodev,noexec` | Исполнение из домашних каталогов |

Детали реализации:

- **размер `/tmp` ограничен** четвертью RAM (256 МБ – 2 ГБ): без `size=` tmpfs может занять до 50% памяти, и любой пользователь, заполнив `/tmp`, выдавит сервисы;
- **`/var/tmp` больше не привязан к `/tmp`**: по FHS он обязан переживать перезагрузку (на это рассчитывают systemd, редакторы, установщики), а tmpfs очищается. Теперь — bind каталога на себя с теми же флагами; старая запись `/tmp /var/tmp none bind` заменяется;
- записи fstab заменяются по точке монтирования (поле 2), комментарии не затрагиваются; повторный запуск не дублирует опции;
- `seclabel` в `/dev/shm` **убрана** — опция работает только с SELinux, Ubuntu использует AppArmor;
- применение через `mount -o remount` без перезагрузки, где это возможно;
- **если `/home` не отдельный раздел** (типично для VPS) — в fstab добавляется bind-монтирование `/home /home none bind,nosuid,nodev,noexec`. Unit `remount-home.service` из v2 удаляется: `mount -o remount /home` не работает, когда `/home` не точка монтирования, и падал при каждой загрузке;
- ⚠️ `noexec` на `/home` запрещает запуск программ из `~/bin`, `~/.local/bin` и т.п.;
- **совместимость noexec /tmp с apt**: часть maintainer-скриптов dpkg выполняется из временного каталога. Скрипт переносит его в `/var/lib/apt/tmp` (`/etc/apt/apt.conf.d/99tempdir`) — без этого ночные unattended-upgrades могли падать с `Permission denied`.

### 10. Параметры ядра (sysctl)

| `kernel.dmesg_restrict` | `1` | — | dmesg недоступен обычным пользователям |
| `kernel.kptr_restrict` | `2` | — | адреса ядра скрыты из /proc и /sys |
| `kernel.sysrq` | `0` | — | Magic SysRq отключён (есть консоль провайдера) |
| `kernel.randomize_va_space` | `2` | 1.5.1 | ASLR максимальный |
| `fs.suid_dumpable` | `0` | 1.5.3 | core dump setuid-процессов запрещён |
| `kernel.core_pattern` | `\|/bin/false` | — | третий уровень блокировки dump (см. секцию 12) |
| `fs.protected_{hardlinks,symlinks}` | `1` | — | классические /tmp-атаки через ссылки |
| `fs.protected_{fifos,regular}` | `2` | — | атаки через FIFO/файлы в sticky-каталогах |
| `kernel.kexec_load_disabled` | `1` | — | подмена ядра без перезагрузки (необратимо до reboot) |
| `kernel.unprivileged_bpf_disabled` | `1` | — | eBPF только для root |
| `net.core.bpf_jit_harden` | `2` | — | усиление JIT eBPF против эксплойтов ядра |
| `dev.tty.ldisc_autoload` | `0` | — | автозагрузка TTY line discipline (класс CVE в `n_hdlc` и др.) |
| `vm.unprivileged_userfaultfd` | `0` | — | userfaultfd, используемый в эксплойтах гонок |

Если часть параметров не применяется (например, IPv6 отключён), `sysctl --system` выдаёт предупреждение, но скрипт продолжает работу.

**User namespaces — подбирается под ядро автоматически:**

- `kernel.unprivileged_userns_clone = 0` — пишется **только если параметр существует** (`/proc/sys/kernel/...`). Это Debian/Ubuntu-патч, отсутствующий на новых ядрах — раньше sysctl молча выдавал ошибку;
- `kernel.apparmor_restrict_unprivileged_userns = 1` — механизм ядер Ubuntu 24.04+/26.04, пишется при наличии.

> ⚠️ Ограничение userns ломает **rootless Docker/Podman**. Если используете контейнеры без root — закомментируйте соответствующие строки в `/etc/sysctl.d/99-hardening.conf` и выполните `sysctl --system`.

### 11. Blacklist модулей ядра

Файл: `/etc/modprobe.d/hardening-blacklist.conf`. Каждый модуль блокируется парой `blacklist` + `install <mod> /bin/false` — вторая директива не даёт подгрузить модуль даже явным `modprobe`.

**Файловые системы с историей уязвимостей** (CIS 1.1.1.x): `cramfs`, `freevxfs`, `jffs2`, `hfs`, `hfsplus`, `udf`. Вектор атаки — автоматическое монтирование специально созданных образов через `udisks2`/automount.

**Сетевые протоколы с историей CVE** (CIS 3.2.1–3.2.4): `dccp`, `sctp`, `rds`, `tipc`. На VPS практически никогда не нужны.

> **VPS-специфика:** USB-storage и Firewire **не блокируются** — на виртуальной машине этих устройств нет, а агрессивный blacklist может задеть virtio-драйверы некоторых провайдеров. `ext*`/`vfat`/`overlay`/`squashfs` не трогаются — это сломало бы корневую ФС, EFI, snap и контейнеры.

После записи — `update-initramfs -u -k all`; полная сила blacklist — после перезагрузки.

### 12. Отключение core dump

Тройная блокировка (CIS 1.5.3) — три механизма покрывают разные классы процессов:

| Уровень | Файл | Покрывает |
|---|---|---|
| `hard core 0` | `/etc/security/limits.conf` | PAM-сессии (интерактивные входы) |
| `Storage=none`, `ProcessSizeMax=0` | `/etc/systemd/coredump.conf.d/disable.conf` | процессы под systemd |
| `kernel.core_pattern = \|/bin/false` | sysctl (секция 10) | всё остальное |

Core dump процесса может содержать пароли, ключи и другие секреты из памяти — на харденированном сервере они не нужны.

### 13. Auditd

**Защита от повторного запуска:** если правила уже immutable (`auditctl -s` → `enabled 2`), секция пропускается с предупреждением — изменить правила можно только после reboot, а попытка рестарта auditd уронила бы скрипт.

**`/etc/audit/auditd.conf`** — лимиты рассчитаны в секции 0:

```
max_log_file        = <квота ÷ 5> МБ        num_logs = 5
max_log_file_action = ROTATE                 log_format = ENRICHED
space_left_action   = SYSLOG                 admin_space_left_action = ROTATE
disk_full_action    = ROTATE  ← не halt/single: VPS без консоли ушёл бы в офлайн
flush = INCREMENTAL_ASYNC     freq = 50
```

Устаревшие `dispatcher = /sbin/audispd` и `disp_qos` **отсутствуют** — они удалены в auditd 3.x (Ubuntu 22.04+), с ними демон мог не стартовать.

**Правила `/etc/audit/rules.d/99-hardening.rules`:**

| Категория | Что отслеживается | Ключ | CIS |
|---|---|---|---|
| Идентификация | `/etc/passwd`, `shadow`, `group`, `gshadow`, `security/opasswd` | `identity` | 6.2.3.8 |
| Привилегии | `/etc/sudoers`, `/etc/sudoers.d/` | `sudoers` | 6.2.3.1 |
| PAM | `/etc/pam.d/`, `/etc/security/`, `login.defs` | `pam` | — |
| SSH | `sshd_config`, `sshd_config.d/`, `~<user>/.ssh/`, `/root/.ssh/` | `sshd_config`, `ssh_keys` | — |
| Входы и сессии | `lastlog`, `faillog`, `faillock`, `utmp`, `wtmp`, `btmp` | `logins`, `session` | 6.2.3.12–13 |
| Cron | все cron-каталоги + `/var/spool/cron/` | `cron` | — |
| Автозагрузка | `/etc/systemd/system/`, `ld.so.preload`, `ld.so.conf.d/` | `systemd`, `preload` | — |
| Время | `adjtimex`/`settimeofday`/`clock_settime` от пользователей, `/etc/localtime` | `time_change` | 6.2.3.4 |
| Хост и сеть | `sethostname`/`setdomainname`, `hosts`, `hostname`, `netplan/`, `resolv.conf` | `system_locale` | 6.2.3.5 |
| AppArmor | `/etc/apparmor/`, `/etc/apparmor.d/` | `mac_policy` | 6.2.3.14 |
| Монтирование | `mount`/`umount2` от пользователей | `mounts` | 6.2.3.10 |
| Права файлов | `chmod`/`chown` и варианты, **b64 + b32**, фильтр `auid>=1000` | `file_perm` | 6.2.3.9 |
| Отказ в доступе | `open`/`openat`/`creat`/`truncate` с `EACCES`/`EPERM` | `access` | 6.2.3.7 |
| Повышение привилегий | `setuid`/`setgid` (b64+b32) от пользователей; `execve` при `euid=0` | `priv_esc`, `priv_exec` | 6.2.3.6 |
| Модули ядра | `/usr/bin/kmod` + syscalls `*_module` (b64+b32) | `kernel_modules` | 6.2.3.19 |
| Сеть | **только `bind`** реальных пользователей (b64+b32) | `net_bind` | — |
| Загрузчик и ядро | `/boot/`, `kexec_load`/`kexec_file_load` | `boot`, `kexec` | — |

Принципиальные решения:

- **правила `socket`/`connect` намеренно отсутствуют** — аудит каждого сетевого вызова генерировал тысячи событий в секунду и был первопричиной ошибки `audit: backlog limit exceeded`; увеличение буфера лечило симптом. Новый слушающий сокет (`bind`) — редкое и действительно значимое событие, он оставлен;
- **дублирование b64 + b32**: без правил для `arch=b32` аудит тривиально обходился 32-битными syscalls;
- фильтр `-F auid>=1000 -F auid!=unset` отсекает шум системных демонов, оставляя действия реальных пользователей; в v3 он добавлен и к `setuid`/`setgid` (их постоянно вызывают cron, sshd, systemd) и к правилам времени (chronyd подстраивает часы непрерывно);
- **`/usr/bin/kmod` вместо `/sbin/insmod`, `rmmod`, `modprobe`**: это симлинки на kmod, и наблюдение `-p x` за симлинком не срабатывает при запуске;
- `-i` в начале правил: если какого-то syscall или пути нет в этой версии ядра/ОС (например, b32 без IA32-эмуляции), остальные правила всё равно загружаются;
- `-b <backlog>` — рассчитан из RAM; `--backlog_wait_time` убран (значение `1` из старой версии *уменьшало* ожидание и увеличивало потери — комментарий был неверным);
- `-f 1` — при сбое аудита писать в syslog, **не** паника ядра (`-f 2`): на VPS без физической консоли паника означает недоступный сервер;
- `-e 2` в конце — правила **неизменяемы до перезагрузки**: злоумышленник не отключит аудит без reboot, который сам оставит след.

**Ротация:** только средствами auditd. Отдельный `/etc/logrotate.d/audit` **не создаётся и удаляется, если был** — auditd держит файл открытым и ротирует сам; параллельный logrotate с рестартом демона давал двойную ротацию и разрывы аудита.

Просмотр событий:

```bash
ausearch -k identity   | tail -20   # изменения passwd/shadow
ausearch -k sudoers    | tail -20   # изменения sudoers
ausearch -k ssh_keys   | tail -20   # изменения SSH-ключей
ausearch -k priv_exec  | tail -20   # команды от root реальными пользователями
ausearch -k net_bind   | tail -20   # новые слушающие сокеты
ausearch -k pam        | tail -20   # изменения PAM
ausearch -k access     | tail -20   # отказы в доступе к файлам
aureport --summary                  # сводка
auditctl -s                         # backlog, lost, enabled
```

### 14. AppArmor

`apparmor`/`apparmor-utils` доустанавливаются при отсутствии (проверка через `dpkg -s`), служба включается, выводится отчёт: сколько профилей загружено и сколько в режиме `complain`.

**Изменено в v3.** v2 переводила в `enforce` все файлы `/etc/apparmor.d/`. Но часть профилей дистрибутив держит в `complain` или с `flags=(unconfined)` намеренно — на 24.04 это десятки профилей, разрешающих программам user namespaces, — и принудительный enforce ломал эти программы. Теперь по умолчанию — только отчёт; переводите профили выборочно:

```bash
aa-status | sed -n '/complain mode/,/^[0-9]/p'   # что в complain
aa-enforce /etc/apparmor.d/<профиль>             # перевести один
```

`APPARMOR_ENFORCE_ALL="yes"` в начале скрипта переводит в enforce все complain-профили, кроме помеченных `unconfined` (CIS 1.3.1.4).

### 15. Настройка sudo

Файл: `/etc/sudoers.d/99-hardening` (права 440).

**Проверка до установки (исправлено в v3).** Root к этому моменту заблокирован, а битый файл в `sudoers.d` ломает sudo целиком — это полная потеря доступа, остаётся только VNC и recovery. Поэтому файл сначала пишется во временный, проверяется `visudo -c -f`, и только потом ставится на место; затем `visudo -c` проверяет sudoers целиком, и при ошибке наш файл убирается. Если проверка не прошла — sudo продолжает работать как раньше.

| Настройка | Значение | Назначение |
|---|---|---|
| `timestamp_timeout=5` | 5 минут | сессия sudo истекает быстро |
| `use_pty` | — | команда в отдельном псевдотерминале: фоновый процесс не перехватит ввод |
| `secure_path` | фиксированный | защита от подмены системных утилит через PATH |

`!visiblepw` убран: это значение по умолчанию. В Ubuntu 25.10+ / 26.04 вместо sudo используется **sudo-rs**, который поддерживает не все `Defaults`, — скрипт использует только общие для обоих.

**Логирование** — через rsyslog (`/etc/rsyslog.d/50-sudo.conf`): все события sudo дублируются в `/var/log/sudo.log` (права 600). Формат записи:

```
Jul 14 03:12:44 server sudo: admin : TTY=pts/0 ; PWD=/home/admin ; USER=root ; COMMAND=/bin/bash
```

Опции `log_output`, `logfile`, `requiretty` **сознательно не используются**: первые две требуют I/O-плагин sudo, не входящий в пакет Ubuntu, третья удалена из sudo 1.9.x — с ними `sudo -i` падал с `unknown setting`.

### 16. Политика паролей

Файл: `/etc/security/pwquality.conf` (CIS 5.3.3.2.x). **С v3 записывается в секции 3, до задания пароля администратора**; секция 16 только проверяет, что политика на месте.

| Параметр | Значение | Смысл |
|---|---|---|
| `minlen` | `16` | минимальная длина |
| `dcredit`/`ucredit`/`lcredit`/`ocredit` | `-1` | минимум 1 цифра / заглавная / строчная / спецсимвол |
| `maxrepeat` | `3` | не более 3 одинаковых символов подряд |
| `dictcheck` | `1` | проверка по словарю cracklib |
| `gecoscheck` | `1` | запрет слов из GECOS |
| `usercheck` | `1` | пароль не должен содержать имя пользователя |
| `enforce_for_root` | — | политика действует и когда пароль задаёт root (иначе — только предупреждение) |
| `retry` | `3` | попыток ввода за один вызов `passwd` |

SSH-вход по паролю отключён — политика защищает пароль для `sudo` и любые будущие локальные УЗ.

### 17. Права на системные файлы

```bash
chown root:shadow /etc/shadow /etc/gshadow
chmod 640 /etc/shadow /etc/gshadow      # CIS 7.1.3–7.1.4
chmod 644 /etc/passwd /etc/group        # CIS 7.1.1–7.1.2
chmod 700 /boot
```

`640 root:shadow` — как в Ubuntu и допускается CIS. При `600` (v2) setgid-утилита `unix_chkpwd` не может читать `/etc/shadow` и проверять пароли для непривилегированных процессов.

SUID снимается с редко используемых утилит `chfn`, `chsh`, `newgrp` — каждая проверяется на существование и наличие бита.

> **Изменение v2:** симлинк `~root/.bash_history → /dev/null` **убран**. Отключение истории — антифорензика: при инциденте она помогает атакующему скрыть следы больше, чем защищает владельца. Команды с правами root аудирует auditd (ключ `priv_exec`) — этот журнал, в отличие от истории shell, защищён immutable-правилами.

### 18. Удаление телеметрии

| Пакет | Назначение |
|---|---|
| `ubuntu-report` | отчёты об использовании системы |
| `popularity-contest` | статистика установленных пакетов |
| `apport` | сбор и отправка crash-репортов |
| `whoopsie` | отправщик crash-репортов в Canonical |

Проверка через `dpkg -s` (не `dpkg -l`, который возвращал успех даже для удалённых пакетов в статусе `rc`), затем `purge` + `autoremove` + `autoclean`. ### 19. Автоматические обновления

**`/etc/apt/apt.conf.d/52unattended-upgrades-hardening`** — собственный файл вместо перезаписи `50unattended-upgrades` из пакета (в v2 при обновлении пакета терялись новые умолчания). Директива `#clear` заменяет списки целиком — без неё apt **дописал** бы наши значения к стандартным.

Разрешённые источники — `-security`, ESM Apps/Infra (Ubuntu Pro), `-updates` (многие исправления безопасности приходят именно через `-updates`, а не `-security`).

Исключения — пакеты с данными и оркестрация, обновление которых должно быть ручным и контролируемым (совпадение по началу имени):

```
docker  containerd  kube  postgresql  mysql  mariadb  redis  mongodb
```

**nginx и apache больше не исключены**: это самые открытые наружу сервисы, их security-исправления важнее короткого перезапуска.

**needrestart** (`/etc/needrestart/conf.d/50-hardening.conf`, режим `a`): после обновления библиотек сервисы перезапускаются автоматически — иначе уязвимая версия остаётся загруженной в память до перезагрузки.

| Параметр | Значение | Причина |
|---|---|---|
| `AutoFixInterruptedDpkg` | `true` | исправлять прерванные установки |
| `MinimalSteps` | `true` | атомарные шаги — безопасное прерывание |
| `Remove-Unused-Dependencies` | `true` | без orphan-пакетов |
| `Automatic-Reboot` | `false` | неожиданный reboot продакшн-VPS недопустим; необходимость видна по `/var/run/reboot-required` |
| `Mail` / `MailOnlyOnError` | `root` / `true` | письмо только при ошибках (нужен MTA; иначе см. `/var/log/unattended-upgrades/`) |

**Расписание** — systemd drop-in (не перезапись unit-файла, чтобы обновления пакетов не затирали настройку):

```
/etc/systemd/system/apt-daily.timer.d/override.conf           →  03:00 ± 10 мин
/etc/systemd/system/apt-daily-upgrade.timer.d/override.conf   →  03:30 ± 10 мин
```

Перед новым `OnCalendar` дефолтные значения сбрасываются пустыми строками — иначе systemd объединяет расписания и таймер срабатывает по обоим. `RandomizedDelaySec=10m` — чтобы VPS одного провайдера не стучались в репозитории одновременно. Проверка: `systemctl list-timers apt-daily*`.

### 19.5. Шифрование LUKS (необязательно)

Скрипт показывает `--luks status` и предлагает меню: отдельный диск, файл-контейнер, защита swap, SSH-разблокировка root. `Enter` — пропустить. Секция стоит до шага 20, чтобы dropbear в initramfs получил `authorized_keys` администратора.

Режим выполняется в подоболочке: ошибка внутри него не прерывает харденинг — скрипт сообщает код и идёт дальше. То же самое можно сделать позже: `bash ubuntu_hardening.sh --luks <режим>`. Подробности — в разделе [Шифрование LUKS](#шифрование-luks-режим---luks).

### 20. Приватный ключ и старые логи

**Логи v2 с ключом.** Все файлы `/root/hardening_*.log`, содержащие приватный ключ (их оставляла v2), затираются `shred`.

**Если использовался свой публичный ключ** — приватного ключа на сервере нет; оставшийся от прошлого прогона `/root/admin_ssh_key` удаляется.

**Если ключ генерировался** — скрипт предлагает показать его ещё раз прямо в терминале (мимо лога), а затем надёжно затереть:

```bash
shred -uz /root/admin_ssh_key    # перезапись + удаление
```

Только после явного подтверждения `y`. Публичный ключ (`.pub`) остаётся на сервере в любом случае.

> **Исправлено в v3.** v2 советовала здесь `scp -P 22 root@<IP>:…`, но к этому моменту root по SSH уже запрещён, а порт сменён — скачать так невозможно. Если ключ не сохранён, единственный путь — показать его ещё раз на этом терминале.

## Шифрование LUKS (режим --luks)

Шифрование встроено в скрипт как режим `--luks`. Полное руководство и восстановление — в **`LUKS.md`**.

**Что LUKS даёт на VPS.** Защищает данные «в покое»: снапшоты и бэкапы у провайдера, отключённые тома, списанные диски, изъятие выключенного сервера. **Не защищает** от гипервизора, читающего RAM работающей ВМ, и от взлома самой работающей системы — там данные уже расшифрованы.

```bash
bash ubuntu_hardening.sh --luks status
bash ubuntu_hardening.sh --luks data /dev/vdb --name pgdata --mount /var/lib/postgresql
bash ubuntu_hardening.sh --luks file /var/lib/secure.img 20G
bash ubuntu_hardening.sh --luks swap
bash ubuntu_hardening.sh --luks remote-unlock --tang http://tang.example.net
```

### Данные Docker

Если шифровать всю ОС избыточно, достаточно зашифровать данные. Для Docker это не только тома — ещё логи контейнеров и их записываемые слои.

```bash
sudo bash ubuntu_hardening.sh --luks data /dev/vdb     # или --luks file /var/lib/secure.img 50G
sudo bash ubuntu_hardening.sh --luks docker
```

- `/var/lib/docker` (и `/var/lib/containerd`, если используется) копируется на том и подключается обратно bind-монтированием — пути и конфиги Docker не меняются;
- пустые точки монтирования делаются неизменяемыми (`chattr +i`), а `docker.service` получает `RequiresMountsFor=` — без открытого тома Docker не стартует и не может писать на открытый диск (иначе, например, Postgres создал бы новую пустую базу прямо на системном диске);
- при ручной разблокировке Docker запускается командой `sudo luks-unlock securedata`, останавливается вместе с томом — `sudo luks-lock securedata`;
- скрипт перечисляет, что **останется незашифрованным**: bind-монтирования вне тома, каталоги compose-проектов (`.env`), логирование в journald;
- старый каталог сохраняется как `*.pre-luks` до явного удаления.

Бэкапы шифруйте отдельно (restic, borg, age), swap — `--luks swap`. Подробнее — `LUKS.md`.

### Шифрование всего сервера

Корень, с которого система работает, нельзя зашифровать «на лету», поэтому два режима:

| | `--luks encrypt-root <раздел>` | `--luks encrypt-root-auto` |
|---|---|---|
| Где запускать | rescue-система провайдера | на самом сервере |
| `/boot` внутри корня | создаёт раздел `/boot` 1 ГБ из конца корня | не поддерживается |
| Пароль | задаётся сразу | после загрузки: `--luks encrypt-root-finish` |
| Ubuntu 26.04 (dracut) | да | нет (только 22.04/24.04) |

Общие требования: **снапшот диска**, VNC-консоль, корень — ext4 на обычном разделе (не LVM), загрузчик GRUB, свободно ≥ 512 МБ.

```bash
# из rescue-системы:
bash ubuntu_hardening.sh --luks encrypt-root /dev/vda1

# или на работающем сервере:
sudo bash ubuntu_hardening.sh --luks encrypt-root-auto      # подготовка + reboot
sudo bash ubuntu_hardening.sh --luks encrypt-root-finish    # сразу после загрузки
```

**`encrypt-root-auto`** добавляет в initramfs временный ключ и сценарий: при следующей загрузке, до монтирования корня, раздел шифруется на месте, затем загрузка продолжается. Обрыв питания — шифрование продолжится при следующей загрузке; не началось — система грузится как раньше (журнал `/boot/luks-convert.log`). **До `encrypt-root-finish` защиты нет** — ключ лежит на незашифрованном `/boot`. Finish задаёт пароль, проверяет каждый initramfs и только потом удаляет временный ключ; предлагает сменить мастер-ключ на случай снапшотов, сделанных в промежутке.

После шифрования пароль нужен при **каждой загрузке**: VNC, SSH (`--luks remote-unlock`, dropbear) или автоматически через Tang. Подробности, ограничения и восстановление — `LUKS.md`.

**Способ разблокировки томов с данными (`--unlock`):**

| Способ | Как работает | Когда выбирать |
|---|---|---|
| `manual` (по умолчанию) | После загрузки том закрыт; после входа — `sudo luks-unlock <имя>` | Ключа на сервере нет вообще — самый сильный вариант |
| `keyfile` | Ключ в `/etc/cryptsetup-keys.d/`, автомонтирование | Root тоже зашифрован или угроза — утечка отдельного volume |
| `tang` | Clevis + Tang: автоматически, пока сервер «видит» ваш Tang | Парк серверов; Tang — у другого провайдера |

Для `manual` сервисы, работающие с этими данными, перечислите в `/etc/luks-unlock.d/<имя>.services` и уберите из автозапуска — `luks-unlock` запустит их после монтирования, `luks-lock` остановит.

**Решения, заложенные в режим:**

- LUKS2, `aes-xts-plain64`/512, argon2id, сектор 4096; если vCPU не отдаёт AES-NI — предупреждение и предложение Adiantum;
- память argon2id ограничена ¼ RAM (64 МБ – 1 ГБ): стоимость фиксируется при форматировании, и дефолт cryptsetup может не дать открыть том на 1-гигабайтном VPS или после понижения тарифа;
- `no_read/no_write_workqueue` сохраняются в заголовке — меньше задержка на virtio/NVMe;
- TRIM выключен по умолчанию: на общем хранилище он раскрывает карту занятых блоков;
- резервная копия заголовка — в `/root/luks-backup/`, её нужно скачать и удалить с сервера;
- `swap`: swap-файл заменяется на zram (swap поверх loop-устройства склонен к взаимоблокировкам), swap-раздел шифруется dm-crypt со случайным ключом при каждой загрузке, адресация по PARTUUID;
- `remote-unlock`: dropbear в initramfs с ключами администратора и принудительной командой `cryptroot-unlock`, сеть через параметр ядра `ip=` (статический IP или DHCP; только IPv4), опционально Tang; порт нужно открыть в firewall **провайдера** — UFW в initramfs не работает;
- деструктивный режим `data` отказывается работать с примонтированным, swap-, LVM- или RAID-устройством и требует ввести путь устройства вручную;
- правила auditd для `/etc/crypttab`, ключей и initramfs — в `/etc/audit/rules.d/60-luks.rules` (при immutable-правилах применятся после reboot).

## Сознательные отклонения от CIS

Эти решения оправданы спецификой VPS/VDS — это **не пробелы**, а осознанный выбор:

| Отклонение | CIS | Причина |
|---|---|---|
| `disk_full_action = ROTATE` (не halt/single) | 6.2.2.3 | halt = недоступный VPS без физической консоли |
| auditd `-f 1` (syslog), не `-f 2` (паника) | — | паника ядра при сбое аудита уронит VPS в офлайн |
| Нет аудита `socket`/`connect` | — | тысячи событий/сек, переполнение backlog; `bind` покрывает значимые случаи |
| USB/Firewire не в blacklist | 1.1.1 | на виртуалке устройств нет; риск задеть virtio-драйверы |
| `chrony` вместо `systemd-timesyncd` | 2.3 | точнее и быстрее восстанавливается на VPS |
| `ptrace_scope = 1`, не `2` | 1.5.2 | сохранить `strace`/`gdb` для диагностики без физического доступа |
| `kernel.sysrq = 0` | — | SysRq не нужен (есть консоль провайдера) и является вектором атаки |
| `Automatic-Reboot = false` | — | неконтролируемый reboot продакшн-VPS недопустим |
| Пароль GRUB не ставится | 1.4.1 | без IP-KVM усложняет восстановление через консоль провайдера |
| userns-ограничения легко отключаемы | — | не ломать rootless-контейнеры без ведома администратора |
| История root не отключается | — | отключение — антифорензика; аудит ведёт auditd |
| AppArmor: complain-профили не форсируются | 1.3.1.4 | часть профилей намеренно в complain; принудительный enforce ломает программы. Включается `APPARMOR_ENFORCE_ALL="yes"` |
| `rp_filter = 2` при нескольких интерфейсах | 3.3.7 | строгий режим ломает асимметричную маршрутизацию с приватной сетью провайдера |

## Подключение после настройки

```bash
# Прямое подключение (пароль ключа при каждом входе)
ssh -p <PORT> -i ./admin_ssh_key <user>@<IP>

# Через ssh-agent (пароль ключа один раз за сессию)
eval $(ssh-agent)
ssh-add ./admin_ssh_key
ssh -p <PORT> <user>@<IP>
```

`~/.ssh/config` на клиентской машине:

```sshconfig
Host myserver
    HostName      <IP>
    Port          <PORT>
    User          <user>
    IdentityFile  ~/.ssh/admin_ssh_key
    AddKeysToAgent yes
```

`<user>` — имя администратора, выбранное при запуске (по умолчанию `admin`).

После этого достаточно: `ssh myserver`

## Диагностика и мониторинг

```bash
# Лог выполнения самого харденинга
ls -la /root/hardening_*.log

# SSH
journalctl -u ssh -u sshd -f              # живой лог
ss -tlnp | grep <PORT>                    # слушает ли порт
systemctl status ssh.socket               # должен быть disabled/inactive!
grep -r "^Port" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/ 2>/dev/null
sshd -T | grep -E '^(port|kexalgorithms|passwordauthentication) '   # итоговые значения

# Fail2ban
fail2ban-client status sshd               # забаненные IP
fail2ban-client status recidive           # повторные нарушители
fail2ban-client set sshd unbanip <IP>     # разбанить вручную

# UFW
ufw status verbose

# Auditd
auditctl -s                               # backlog, lost (должно быть 0), enabled
ausearch -k identity   | tail -20
ausearch -k ssh_keys   | tail -20
ausearch -k priv_exec  | tail -20
ausearch -k net_bind   | tail -20
aureport --summary

# AppArmor
aa-status

# su / PAM
grep pam_wheel /etc/pam.d/su              # должна быть активная строка с group=sudo

# NTP / Chrony
chronyc tracking                          # источник и погрешность
chronyc sources -v
timedatectl show

# Разделы
findmnt /tmp /var/tmp /dev/shm /home      # проверка флагов noexec/nosuid/nodev

tail -20 /var/log/sudo.log
visudo -c

# LUKS

# Автообновления
systemctl list-timers apt-daily*
cat /var/log/unattended-upgrades/*.log

```

## Что требует перезагрузки

- **Blacklist модулей ядра** — DCCP, SCTP, RDS, TIPC и редкие ФС
- **Ограничения user namespaces** — на части ядер применяются только после reboot
- **`/var/tmp` и `/home` bind-mount** — если не применились в текущей сессии (например, `/var/tmp` уже был смонтирован по схеме v2)
- **Любые изменения правил auditd** — при действующем immutable-режиме (`-e 2`), включая `60-luks.rules`
- **SSH-разблокировка root** (`--luks remote-unlock`) — проверяйте первую перезагрузку с открытой VNC-консолью
- **`--luks encrypt-root-auto`** — шифрование корня происходит именно при перезагрузке; сразу после неё — `--luks encrypt-root-finish`

```bash
reboot
# затем проверка доступности:
ssh -p <PORT> -i ./admin_ssh_key <user>@<IP>
```

## Восстановление при потере доступа

Все изменяемые конфиги бэкапятся с меткой времени. Через консоль провайдера (VNC/KVM):

```bash
# SSH: откат конфига
cp /etc/ssh/sshd_config.bak.<timestamp> /etc/ssh/sshd_config
systemctl restart ssh

# SSH: вернуть перемещённые drop-in (если они были нужны)
cp /root/sshd_config.d.bak/* /etc/ssh/sshd_config.d/ 2>/dev/null

# Разблокировать root (для входа через консоль провайдера)
passwd -u root && passwd root

# fstab: откат (если система не грузится из-за раздела — режим recovery)
cp /etc/fstab.bak.<timestamp> /etc/fstab

# su: откат pam_wheel
cp /etc/pam.d/su.bak.<timestamp> /etc/pam.d/su

# chrony: откат конфига
cp /etc/chrony/chrony.conf.bak.<timestamp> /etc/chrony/chrony.conf && systemctl restart chrony

# LUKS: откат crypttab/fstab, разблокировка вручную
ls /root/luks-backup/
cryptsetup open /dev/vdb securedata && mount /dev/mapper/securedata /srv/secure

# UFW: экстренно выключить
ufw disable

# Fail2ban: снять бан со своего IP
fail2ban-client set sshd unbanip <ваш_IP>

# Разбор причин: лог харденинга
less /root/hardening_*.log
```

Если SSH не поднимается после правок — смотреть `journalctl -xe -u ssh -u sshd` и проверить, не включился ли обратно `ssh.socket` (`systemctl status ssh.socket`).

## Повторный запуск скрипта

Скрипт можно запускать повторно, с оговорками:

- **auditd**: пока правила immutable (`enabled 2`), секция 13 пропускается с предупреждением; файлы в `/etc/audit/` при этом уже содержат нужную конфигурацию и применятся после reboot;
- **root заблокирован** — запускайте через `sudo -i` из-под администратора;
- дубликаты не плодятся: `authorized_keys` дедуплицируется через `sort -u`, а ключ прошлого прогона удаляется; записи `127.0.1.1` в `/etc/hosts` заменяются; fstab-строки заменяются по точке монтирования, опции `/home` не дублируются; строка `pam_wheel` не дублируется; `usermod -aG sudo` идемпотентен;
- **переход с v2**: `remount-home.service` удаляется, `/var/tmp` переводится на собственный bind (после reboot), логи v2 с приватным ключом затираются, файл `50unattended-upgrades` из v2 переопределяется `52-…`;
- `ufw --force reset` снова сбросит правила — дополнительные порты придётся указать заново в диалоге секции 6.

## Ручное включение форвардинга

Если сервер используется как VPN-сервер или прокси:

```bash
# Вариант 1: в переменных в начале скрипта перед запуском
TCP_FORWARDING="yes"
GATEWAY_PORTS="yes"     # только если нужен проброс портов наружу

# Вариант 2: после запуска — отредактировать sshd_config
sed -i 's/^AllowTcpForwarding no/AllowTcpForwarding yes/' /etc/ssh/sshd_config
sshd -t && systemctl restart ssh

# Плюс разрешить форвардинг в UFW и sysctl:
ufw route allow in on eth0
sysctl -w net.ipv4.ip_forward=1
# и закрепить в /etc/sysctl.d/99-hardening.conf (net.ipv4.ip_forward = 1)
```
