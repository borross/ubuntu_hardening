# Шифрование LUKS2 для ubuntu_hardening (VPS/VDS)

Шифрование встроено в `ubuntu_hardening.sh` (v3.1) как режим `--luks`, включая шифрование всего корня сервера.
Его можно запустить в любой момент после харденинга или выбрать в
необязательной секции 19.5 полного прогона. Справка: `bash ubuntu_hardening.sh --help`.

## 1. Что LUKS даёт на VPS, а что нет

| Сценарий | Защищает? |
|---|---|
| Утечка снапшота / бэкапа диска у провайдера | Да |
| Списанный или переданный другому клиенту диск | Да |
| Отключённый и подключённый к чужой ВМ том (volume) | Да |
| Изъятие выключенного сервера | Да |
| Гипервизор / сотрудник провайдера читает RAM работающей ВМ | **Нет** — мастер-ключ в памяти |
| Взлом работающей системы (RCE, украденный SSH-ключ) | **Нет** — данные уже расшифрованы |

Против доступа к RAM помогают только конфиденциальные ВМ (AMD SEV-SNP / Intel TDX),
если провайдер их предлагает. LUKS — защита данных «в покое», а не замена остальному харденингу.

## 2. Какой режим выбрать

| Ситуация | Команда | Разблокировка |
|---|---|---|
| Есть второй диск/volume под данные | `--luks data /dev/vdb` | см. `--unlock` |
| Второго диска нет, нужен защищённый каталог | `--luks file /var/lib/secure.img 20G` | см. `--unlock` |
| На диске есть swap | `--luks swap` | автоматически |
| **Зашифровать весь сервер (корень)** из rescue-режима | `--luks encrypt-root /dev/vda1` | пароль при загрузке |
| **Зашифровать весь сервер (корень)** с работающей системы | `--luks encrypt-root-auto` → reboot → `--luks encrypt-root-finish` | пароль при загрузке |
| **Данные Docker** (тома, логи, слои контейнеров) | `--luks data /dev/vdb` (или `file`), затем `--luks docker` | Docker стартует после `luks-unlock` |
| Корень уже зашифрован, нужен ввод пароля по сети | `--luks remote-unlock` | SSH в initramfs (22.04/24.04) или Tang |
| Проверить состояние | `--luks status` | — |

`--unlock` для томов с данными:

- **manual** (по умолчанию) — после перезагрузки том закрыт, вы входите по SSH и
  выполняете `sudo luks-unlock securedata`. Ключа на сервере нет вообще — самый
  сильный вариант. Сервисы, работающие с этими данными, перечислите в
  `/etc/luks-unlock.d/securedata.services` и уберите из автозапуска.
- **keyfile** — ключ лежит в `/etc/cryptsetup-keys.d/`, том монтируется сам.
  Имеет смысл, только если root тоже зашифрован или если угрозой является
  утечка именно отдельного volume.
- **tang** — авторазблокировка, пока сервер «видит» ваш Tang-сервер
  (`--unlock tang --tang http://tang.example.net`). Tang держите у другого провайдера и
  открывайте его только для своих серверов. Если Tang недоступен — работает
  обычный пароль.

Пример:

```bash
sudo bash ubuntu_hardening.sh --luks data /dev/vdb \
     --name pgdata --mount /var/lib/postgresql --unlock manual
```

## 3. Решения, заложенные в модуль

- **LUKS2, aes-xts-plain64/512, argon2id, сектор 4096.** Если vCPU не отдаёт
  AES-NI — скрипт предупредит и предложит Adiantum
  (`--cipher xchacha12,aes-adiantum-plain64 --key-size 256`).
- **Память Argon2id ограничена ¼ RAM (64 МБ – 1 ГБ).** Стоимость фиксируется
  при форматировании; дефолт cryptsetup (до 1 ГБ) может не дать открыть том
  на 1-гигабайтном VPS или после понижения тарифа.
- **`no_read/no_write_workqueue`** сохраняются в заголовке (`--persistent`) —
  заметно снижают задержку на virtio/NVMe. Если ядро не поддерживает — откат.
- **TRIM выключен** по умолчанию: на общем хранилище он раскрывает карту
  занятых блоков. `--discards`, если важнее производительность/место.
- **Резервная копия заголовка** кладётся в `/root/luks-backup/` — скачайте и
  удалите. Повреждённый заголовок = потерянные данные.
- **Swap-файл заменяется на zram**, а не шифруется: swap поверх loop-устройства
  на файле склонен к взаимоблокировкам при нехватке памяти. Swap-раздел
  шифруется dm-crypt со случайным ключом при каждой загрузке (адресация по
  PARTUUID, чтобы mkswap никогда не попал не в тот раздел).
- **auditd**: правила для `/etc/crypttab`, ключей и initramfs пишутся в
  `/etc/audit/rules.d/60-luks.rules` (раньше `99-…` с `-e 2`, поэтому
  применятся при следующей загрузке, если правила уже immutable).
- Деструктивный режим `data` откажется работать с примонтированным,
  swap-, LVM- или RAID-устройством и требует ввести путь устройства вручную.

## 4. Данные Docker: `--luks docker`

Если шифровать всю ОС избыточно, достаточно зашифровать то, где лежат данные.
Для Docker это не только тома:

| Что | Где по умолчанию | После `--luks docker` |
|---|---|---|
| Именованные тома | `/var/lib/docker/volumes` | на зашифрованном томе |
| Логи контейнеров (json-file) | `/var/lib/docker/containers` | на зашифрованном томе |
| Записываемые слои и образы | `/var/lib/docker`, в Docker 29+ — `/var/lib/containerd` | на зашифрованном томе |
| bind-монтирования (`/opt/app:/data`) | где укажете | **не переносятся** — скрипт их перечислит |
| `.env`, compose-файлы | каталог проекта | **не переносятся** — скрипт перечислит каталоги проектов |

```bash
sudo bash ubuntu_hardening.sh --luks data /dev/vdb      # или: --luks file /var/lib/secure.img 50G
sudo bash ubuntu_hardening.sh --luks docker
```

Что делает режим:

1. Находит том (`--name`, по умолчанию `securedata`), проверяет, что он открыт и
   смонтирован, что места хватает. Docker из snap не поддерживается.
2. Показывает, что **останется незашифрованным**: bind-монтирования вне тома,
   каталоги compose-проектов, логирование в journald/syslog.
3. Останавливает контейнеры (явно — на случай `live-restore`) и Docker, копирует
   каталог данных (`rsync -aHAXS`: жёсткие ссылки, xattr overlay, sparse), сверяет
   число объектов.
4. Старый каталог переименовывает в `*.pre-luks`, на его месте — пустая
   **неизменяемая** точка монтирования (`chattr +i`), подключённая bind-монтированием
   с тома. Пути не меняются, `daemon.json` и `config.toml` не трогаются.
5. `docker.service` (и `containerd.service`) получают `RequiresMountsFor=` — без
   открытого тома Docker **не может** стартовать и писать на открытый диск.
   Пустая точка монтирования самого тома тоже становится неизменяемой.
6. При ручной разблокировке (`--unlock manual`): автозапуск Docker отключается,
   его запускает `sudo luks-unlock <имя>`; `sudo luks-lock <имя>` останавливает
   Docker, отмонтирует всё и закрывает том.
7. Запускает Docker, проверяет каталог данных, поднимает контейнеры, которые
   работали до переноса. Затем предлагает удалить `*.pre-luks` — это **открытая
   копия данных**; удаляйте после проверки.

Повторный запуск безопасен: перенесённое не трогается, настройки перепроверяются.

**Проверено** на живом Docker: перенос с работающими контейнерами (том, bind,
перезапуск), цикл `luks-lock` → `luks-unlock` с сохранением данных, запрет записи
в пустые точки монтирования, повторный запуск.

**Ещё про утечки:** `--luks swap` (память контейнеров на диске), отдельное
шифрование бэкапов (restic, borg, age), логирование `json-file` или `local`
вместо journald.

## 5. Шифрование всего сервера (корневой ФС)

Зашифровать раздел, с которого система сейчас работает, «на лету» нельзя, поэтому
есть два режима: из rescue-системы провайдера и с работающей системы — тогда
шифрование выполняется при следующей загрузке, до монтирования корня.

### Что нужно в обоих случаях

- **Снапшот диска** в панели провайдера — обязательно.
- **VNC-консоль** провайдера: пароль при загрузке вводится в ней, если не настроена
  сетевая разблокировка; в ней же виден ход шифрования.
- Корень — **ext4 на обычном разделе** (не LVM, не RAID), загрузчик **GRUB**.
  XFS не умеет уменьшаться, а место под заголовок LUKS (32 МБ) берётся уменьшением ФС.
- Свободное место в корне: от 512 МБ (скрипт проверяет оценкой `resize2fs -P`).

После шифрования **каждая загрузка требует пароль**: VNC, SSH (dropbear, 22.04/24.04)
или автоматически через Tang. `/boot` остаётся незашифрованным — так устроена
загрузка Linux; провайдер технически может подменить ядро.

### Из rescue-системы: `--luks encrypt-root`

Подходит для любого раскроя: **если `/boot` внутри корня, скрипт сам создаёт
раздел `/boot` (1 ГБ)**, отрезав его от конца корневого раздела. Пароль задаётся
сразу.

```bash
# 1. На сервере (пока он работает) — по желанию, SSH-разблокировка заранее:
sudo bash ubuntu_hardening.sh --luks remote-unlock --prepare

# 2. В панели провайдера: снапшот, загрузка в rescue-режим.
# 3. В rescue-системе:
wget -O ubuntu_hardening.sh https://raw.githubusercontent.com/borross/ubuntu_hardening/refs/heads/main/ubuntu_hardening.sh
lsblk -f                                    # найти корневой раздел Ubuntu
bash ubuntu_hardening.sh --luks encrypt-root /dev/vda1
```

Что делает скрипт:

1. Проверяет: раздел не смонтирован, ext4, на нём Ubuntu с GRUB, cryptsetup ≥ 2.4.
   Недостающие утилиты в rescue-системе доустанавливает через apt.
2. Показывает план и просит ввести путь раздела для подтверждения.
3. **Если `/boot` не отдельный:** проверяет, что корень — последний раздел диска,
   уменьшает ФС, сохраняет таблицу разделов (`/root/luks-backup/ptable-*.sfdisk`,
   копия — на новом `/boot`), уменьшает раздел, создаёт раздел `/boot` 1 ГБ,
   копирует туда `/boot` и прописывает его в fstab.
4. Шифрует раздел на месте (`cryptsetup reencrypt --encrypt`), спрашивая пароль
   дважды; растягивает ФС обратно.
5. В chroot: при необходимости ставит `cryptsetup-initramfs` (или `systemd-cryptsetup`
   на dracut), пишет `/etc/crypttab`, отключает `GRUB_FORCE_PARTUUID` и growpart
   cloud-init, пересобирает initramfs, `update-grub`. Если `/boot` создавался —
   переустанавливает GRUB для BIOS и перенаправляет загрузочную заглушку на EFI.
6. Проверяет, что каждый initramfs содержит настройку шифрования, а `grub.cfg`
   задаёт корень по UUID ФС.
7. Сохраняет резервную копию заголовка LUKS — **скачайте её до перезагрузки**,
   rescue-система временная.

Если rescue-сессия оборвётся во время шифрования, данные не теряются:

```bash
cryptsetup repair /dev/vda1 && cryptsetup reencrypt --resume-only /dev/vda1
```

Ограничение: если после корневого раздела на диске есть другие разделы, места
под `/boot` взять неоткуда — тогда только переустановка (ниже).

### С работающей системы: `--luks encrypt-root-auto`

Без rescue-режима. Требует **отдельный раздел `/boot`** (в облачных образах
Ubuntu 24.04 он обычно есть — раздел 16; проверка: `findmnt /boot`) и
initramfs-tools, то есть Ubuntu 22.04 / 24.04.

```bash
sudo bash ubuntu_hardening.sh --luks encrypt-root-auto     # подготовка + перезагрузка
# ... сервер шифрует корень при загрузке и загружается сам ...
sudo bash ubuntu_hardening.sh --luks encrypt-root-finish   # пароль вместо временного ключа
```

Как это работает:

1. **Подготовка.** Создаётся временный ключ, в initramfs добавляется сценарий
   шифрования (образ initramfs — с правами 600). `GRUB_FORCE_PARTUUID` отключается,
   проверяется, что корень в `grub.cfg` задаётся по UUID ФС. Если initramfs собрался
   без сценария — всё откатывается.
2. **Перезагрузка.** До монтирования корня сценарий: проверяет ФС, уменьшает её
   на 64 МБ, шифрует раздел временным ключом, открывает его, растягивает ФС и
   продолжает загрузку. Ход виден в VNC, журнал — `/boot/luks-convert.log`.
   - Обрыв питания во время шифрования — при следующей загрузке оно восстанавливается
     (`cryptsetup repair`) и продолжается.
   - Если шифрование не началось (ошибка ФС, мало места) — ФС возвращается к
     прежнему размеру, система грузится как раньше, а повторных попыток не будет
     до разбора причины (флаг `/boot/luks-convert.failed`).
3. **`encrypt-root-finish`.** Задаёт пароль, пишет `/etc/crypttab`, предлагает
   SSH-разблокировку (dropbear), пересобирает initramfs и **проверяет каждый образ**:
   есть настройка шифрования и нет временного ключа. Только после этого ключ
   удаляется из заголовка LUKS и с диска. Если проверка не прошла — сценарий и
   ключ возвращаются, система по-прежнему загрузится.
4. **Смена мастер-ключа (предлагается).** Пока ключ лежал на незашифрованном
   `/boot`, снапшот диска, сделанный в этот промежуток, позволяет извлечь
   мастер-ключ тома. Смена мастер-ключа (`cryptsetup reencrypt` на работающей
   системе) это исключает; иначе удалите такие снапшоты.

> ⚠️ **Между перезагрузкой и `encrypt-root-finish` защиты нет**: ключ лежит рядом
> с диском. Выполняйте finish сразу после загрузки.

Отменить подготовку до перезагрузки: `sudo bash ubuntu_hardening.sh --luks encrypt-root-cancel`.

### Переустановка с шифрованием

Если провайдер позволяет загрузить свой ISO: установщик Ubuntu Server →
«Use an entire disk» → «Set up this disk as an LVM group» → **«Encrypt the LVM
group with LUKS»**. Затем `ubuntu_hardening.sh` и `--luks remote-unlock`.
Единственный вариант для корня на LVM.

### Ubuntu 26.04 (dracut)

С 25.10 initramfs в Ubuntu собирает **dracut**, а не initramfs-tools. Отсюда:

- `encrypt-root` (rescue) поддерживает dracut: ставит `systemd-cryptsetup`, добавляет
  `rd.luks.name=…` в параметры ядра, пересобирает образы `dracut --regenerate-all`;
- `encrypt-root-auto` на dracut **не поддерживается** — используйте rescue-режим;
- SSH-разблокировка через dropbear-initramfs на dracut **не работает**;
  `--luks remote-unlock --tang URL` настраивает Tang (`clevis-dracut`), без Tang —
  пароль в VNC.

### Что проверено

Без реальной перезагрузки VPS: вырезание `/boot` из корневого раздела (GPT), шифрование на
месте с независимой расшифровкой и сверкой контрольных сумм данных, обрыв
шифрования с последующим восстановлением (`repair` + `--resume-only`), все ветви
загрузочного сценария в busybox (шифрование, продолжение после обрыва, пропуск
после сбоя, отказ при нехватке места), сборка настоящего initramfs Ubuntu 24.04 с
этим сценарием. **Полную загрузку на VPS здесь проверить нельзя — первый прогон
делайте на тестовом сервере со снапшотом.**

## 6. Секция 19.5 полного прогона

В полном прогоне после автообновлений (и до удаления ключа в шаге 20, чтобы
dropbear получил `authorized_keys` администратора) скрипт показывает
`--luks status` и предлагает меню: диск, файл-контейнер, swap,
сетевая разблокировка root, перенос данных Docker, **шифрование всего корня** (`encrypt-root-auto`; сам
скрипт в этом случае не перезагружает сервер — перезагрузка после его завершения)
и, если шифрование уже подготовлено, его завершение. Enter — пропустить. Ошибка в режиме LUKS не прерывает
харденинг: режим выполняется в подоболочке, скрипт сообщает код и идёт дальше.

Имя администратора режим `--luks` берёт из `/etc/ubuntu_hardening.conf`,
который пишет полный прогон; переопределяется опцией `--user`.

Пароли LUKS cryptsetup запрашивает без эха, поэтому в лог выполнения они не
попадают.

## 7. Восстановление

```bash
# Том не открывается после смены тарифа (мало RAM для argon2id) — с машины с бо́льшей RAM:
cryptsetup luksConvertKey --pbkdf-memory 131072 /dev/vdb
# Повреждён заголовок:
cryptsetup luksHeaderRestore /dev/vdb --header-backup-file luks-header-….img
# Root: initramfs не поднял сеть — VNC-консоль, ввести пароль там,
# затем проверить ip= в /etc/default/grub.d/90-luks-remote-unlock.cfg
# Откат конфигов: /root/luks-backup/<файл>.<дата>

# ── Шифрование корня (encrypt-root / encrypt-root-auto) ──
# Обрыв во время шифрования (rescue или initramfs-шелл):
cryptsetup repair /dev/vda1 && cryptsetup reencrypt --resume-only /dev/vda1
#   для encrypt-root-auto добавьте --key-file <ключ>; ключ лежит внутри initramfs:
unmkinitramfs /boot/initrd.img-<версия> /tmp/i && ls /tmp/i/main/etc/luks-convert/
# Почему не зашифровалось при загрузке:
cat /boot/luks-convert.log
# Повторить после устранения причины: удалить флаг и перезагрузиться
sudo rm /boot/luks-convert.failed
# Отказаться от автошифрования:
sudo bash ubuntu_hardening.sh --luks encrypt-root-cancel
# Вернуть таблицу разделов (только если шифрование НЕ начиналось):
sfdisk /dev/vda < /root/luks-backup/ptable-<дата>.sfdisk
# Полный откат — снапшот в панели провайдера.

# ── Docker (--luks docker) ──
# Docker не стартует после перезагрузки — так и задумано при --unlock manual:
sudo luks-unlock securedata
# Вернуть Docker на системный диск (пока *.pre-luks не удалён):
sudo luks-lock securedata                       # или: systemctl stop docker docker.socket
sudo sed -i '\|/var/lib/docker none bind|d' /etc/fstab
sudo rm /etc/systemd/system/docker.service.d/10-luks-data.conf
sudo chattr -i /var/lib/docker && sudo rmdir /var/lib/docker
sudo mv /var/lib/docker.pre-luks /var/lib/docker
sudo systemctl daemon-reload && sudo systemctl enable --now docker.socket docker.service
```
